## はじめに

エージェントを回していると、判断を挟みたい箇所が増えます。CI が落ちたとき、リトライするのか、自動修正を試すのか、人を呼ぶのか。社内から上がってきたイシューを、どのチームに渡すのか、書き直しを頼むのか。

エージェントを回し続けるには、ループのどこで判断を挟み、どこで人間に渡すかを決めなければなりません。本記事ではこれを**ループエンジニアリング**と呼びます。自動で進めてよい場面、情報を足して投げ直すべき場面、人を呼ぶべき場面を、コードが区別できる形にする作業です。

こうした振り分けに、[Jev](https://docs.typesafe.ai/) のような「文章を返さず、型のついた答えと確率を返すモデル」が使えます。そして使い始めると、たいてい `confidence` に閾値を置くところから設計が始まります。高ければ自動で処理し、低ければ人に回す。公式ドキュメントもその三分割を勧めていますし、実際うまくいく場面もあります。

ところが、高い `confidence` が何を保証しているのかは、思ったより狭いのです。筆者は「材料が足りないときは confidence が下がるはずだ」と思い込んで実験を組み、**予測と正反対の結果**を得ました。情報を削るほど confidence は上がったのです。

この記事は、その実測の記録です。CI 失敗の振り分け、社内イシューのトリアージ、エージェントのループ制御、レビュー指摘の採否、ログ監視の五つを、それぞれ `confidence` の違う読み方の事例として並べます。書いてあるのは実際に測った数字だけで、アーキテクチャの一般論は入れていません。

## TL;DR

- `confidence` は **`probabilities` から計算される統計量**です。第二の独立した指標ではありません。実測した返り値は、公式ドキュメントが開示している式 `(n × peak − 1) / (n − 1)` と一致しました。
- したがって `confidence` が測っているのは **こちらが並べた選択肢の中での、答えの割れ方** だけです。材料が足りているかも、答えが正しいかも測っていません。
- **材料不足は、低い confidence ではなく「根拠のない答えへの高い confidence」として現れます。** 同じ state に同じ質問を投げ、選択肢だけを変えた対照実験で確認しました。
- 対策は閾値の調整ではなく、**選択肢に「判断できない」を入れること**です。入れた瞬間、同じ材料不足が `cannot_tell` 1.00 として返るようになりました。
- 材料の足り具合は **別の Noul** で取り、`confidence` より先に見ます。順序を逆にすると、最も危険な状態が素通りします。
- 低い confidence にも二種類あります。`cannot_tell` を入れて聞き直すと、**証拠の食い違い**（選ばない）と**材料不足**（それが勝つ）を見分けられます。
- `cannot_tell` を足しても、材料が十分なら答えは変わりません（奪う確率は 0.01〜0.02）。ただし**選択肢の数が変わると confidence の目盛りが変わる**ので、閾値は選択肢数ごとに決め直します。
- Jev はほぼ決定論的（ばらつき ±0.02）なので、**低い confidence にリトライで応じても無駄**です。変えるべきは state か運用方針です。

実測は計 41 リクエストです。以下、順に見ていきます。

## Jev の呼び出しと confidence の定義

まずは Jev がどういうモデルで、`confidence` がどう計算されているかを押さえます。この節の内容が、以降のすべての判断の土台になります。

### Jev に何を渡して何が返るか

![Jev の呼び出し構造。左に判断材料を入れる state と、Choice / Score / Noul を並べる questions があり、それが jev-1.13 に入って、右に choice、confidence、noul という型のついた answers が返る](/images/jev-conf-io.png)

Jev は文章を生成しません。判断材料（`state`）と、型のついた問い（`questions`）を渡すと、こちらが定義した答えの集合の中から選んで返します。コードがそのまま `if` で分岐できる値が返ってくる、と考えてください。

まずは実際のリクエストと返り値を見てみましょう。自動レビューの指摘を処理する例です。

```python
from typesafe_sdk import TypeSafeClient, Choice, Noul

with TypeSafeClient() as client:
    r = client.system_one(
        state={
            "diff": "+def compute_refund(amount, proration_days):\n"
                    "+    unused = amount * 0\n"
                    "+    return round(amount * proration_days / 30)\n",
            "finding": "`unused` is assigned but never read. Remove it.",
        },
        questions={
            "disposition": Choice(
                instructions="How should this automated review finding be handled?",
                criteria={
                    "auto_fix": "Apply the suggested change without a person looking at it",
                    "human_review": "A person should decide before anything changes",
                    "dismiss": "The finding is not correct or not worth acting on",
                },
            ),
            "grounded": Noul(
                instructions="The finding is supported by the code shown in the diff."
            ),
        },
    )

r.choices["disposition"].choice       # "auto_fix"
r.choices["disposition"].confidence   # 0.93
r.nouls["grounded"].noul              # 0.98
```

質問の型は三つあります。

- **Choice**：定義した選択肢から一つを選びます。各選択肢の確率と `confidence` が付きます。
- **Score**：順序のある段階（「様子見でよい」「今週中」「即時」など）のどこに位置するかを返します。確率と `confidence` が付きます。
- **Noul**：ある文が成り立つ確率を 0 から 1 で返します。`confidence` は付きません。

ここで一つ、後で効いてくる性質があります。`questions` に並べた問いは、同じ `state` に対してまとめて評価されます。一回のリクエストで複数の信号を取れるので、この記事で繰り返し出てくる「二つの信号を別々に取る」という設計が、追加のリクエストなしで実現できます。

### confidence は分布の尖り具合

![3択の確率分布を2つ並べた棒グラフ。確率が一つに集中した 0.07/0.92/0.01 は confidence 0.88、散らばった 0.60/0.04/0.36 は confidence 0.40 になる](/images/jev-conf-confidence-shape.png)

ここからが本題です。`confidence` は第二の独立した指標ではありません。`probabilities` から計算される統計量です。

公式ドキュメントが計算式まで開示しているので、実測値と突き合わせてみました。

| Choice の probabilities | 返り値 confidence | 開示式 |
|---|---|---|
| [0.60, 0.04, 0.36] | 0.400 | 0.400 |
| [0.07, 0.92, 0.01] | 0.880 | 0.880 |
| [0.00, 1.00, 0.00] | 1.000 | 1.000 |

一致しました。確率が一つの選択肢に集まれば高く、散らばれば低い。それだけの数字です。

:::message
**式の意味をかみくだくと**

選択肢が3つあるとき、いちばん迷っている状態は「どれも同じくらい」、つまり3つとも 33%（= 1/3）です。逆にいちばん迷っていない状態は、どれか1つが 100% です。

`confidence` は、この2つを 0 と 1 に決めておいて、**いま一番大きい確率がそのあいだのどこにいるか**を測っているだけの数字です。

- 一番大きい確率が 1/3（33%）のとき → confidence は 0
- 一番大きい確率が 1（100%）のとき → confidence は 1

式 `(n × peak − 1) / (n − 1)` の `peak` が「一番大きい確率」、`n` が「選択肢の数」です。3択なら `(3 × peak − 1) / 2` になります。上の表の2行目で確かめてみましょう。一番大きい確率は 0.92 なので、

```
(3 × 0.92 − 1) / 2 = (2.76 − 1) / 2 = 1.76 / 2 = 0.88
```

表の confidence 0.880 と同じ値になりました。1行目も `(3 × 0.60 − 1) / 2 = 0.40` です。選択肢が4つなら、割る数が 2 ではなく 3 になります。

ここで大事なのは、**この式に出てくるのが確率の数字だけ**ということです。`state` に何が書いてあったか、答えが当たっていたか、判断材料が十分だったか。そういったものは式のどこにも入っていません。だから `confidence` は、正しさも情報の多さも教えてくれないのです。
:::

ここから二つのことが出てきます。第一に、`confidence` が測っているのは**こちらが並べた選択肢の中での、答えの割れ方**です。判断材料が足りているかどうかも、答えが正しいかどうかも測っていません。第二に、`confidence` は `probabilities` の関数なので、確率と独立に動くことはありません。「確率は割れているが確信はある」という状態は、構成上つくれないのです。

### Choice、Score、Noul それぞれの confidence 値

三つの型はどれも、内側では選択肢や段階に対する確率分布を返しています。`confidence` はその分布を要約した数字で、意味は共通です。ただし**型をまたいで同じ数字として扱うことはできません**。

| | 返るもの | confidence | 再現 | 注意 |
|---|---|---|---|---|
| Choice | 選んだ選択肢と、各選択肢の確率 | あり | 開示式と一致（3択と4択で確認） | 選択肢の数が変わると目盛りも変わる |
| Score | score（期待値）と、各段階の確率 | あり | 3段階なら一致。段階が増えるほど返り値のほうが高くなる傾向があり、式は不明 | Choice とも、段階数の違う Score とも互換ではない |
| Noul | noul（0〜1）だけ | なし | `2 × noul − 1` の絶対値で作れる | 0.5 は「中くらい」ではなく「どちらとも言えない」 |

Choice の `confidence` は再現できるので、API から返ってこなくても困りません。ドキュメントも、便利な既定値として提供しているだけでこの定義に縛られる必要はない、だから `probabilities` を丸ごと返しているのだ、と書いています。用途に合わないと感じたら、上位2つの差やエントロピーなど、別の尺度に差し替えて構いません。

Score で気をつけたいのは、`score` が期待値だということです。1.5 という値が「段階1と2に半々で割れている」のか「もっと広く散った結果たまたま中間になった」のかは、値だけでは区別できません。分岐に使うなら `probabilities` か `confidence` を併せて見ます。

Noul にはもう一点あります。ある命題とその否定を別々の Noul で聞いても、足して 1 になりません。実測では「不当に安い」0.07 と「妥当である」0.05 が両立しました。どちらの命題も支持されない状態を表現できるのは利点ですが、確率を足して検算することはできません。

## confidence が答えていないこと

計算方法が分かると、この数値が答えていない問いも決まります。判断材料が足りているかどうかが、それにあたります。ここでは高い場合と低い場合を順に見ていきます。

### 高い confidence が意味しないこと

![同一の state から選択肢集合だけを分岐させた対照実験の図。cannot_tell なしでは real_regression に confidence 0.80、cannot_tell ありでは cannot_tell に confidence 0.99 が返る](/images/jev-conf-cannot-tell-ab.png)

まずは高いほうからです。高い `confidence` は、材料が足りていることを意味しません。

想定しているのは、求人情報が次々に流れてくるパイプラインです。一件ずつ「提示額は相場と比べてどうか」を判定し、安すぎるものに印をつけていく、といった処理を考えてください。たいていの求人票には職種も勤務地も書かれていますが、取り込みに失敗したり記載が抜けていたりする一件が、ときどき混ざります。**その欠けた一件が来たときに何が起きるか**が、ここでの問題です。

これを確かめるために、同じ `state` に同じ質問文を投げ、選択肢だけを変えて測りました。

```
state: {"offer": "$150,000 per year"}     ← 職種も勤務地も書かれていない
質問:  この提示額は相場と比べてどうか

  A. 選択肢3つ  below_market / at_market / above_market
       → at_market      確率 0.93   confidence 0.89

  B. 選択肢4つ  below_market / at_market / above_market / cannot_tell
       → cannot_tell    確率 1.00   confidence 1.00
```

```
state: {"job": "unit-tests", "log": "CI failed."}     ← ログ本体がない
質問:  この CI 失敗の原因として最も確からしいものはどれか

  A. 選択肢3つ  flaky_infra / real_regression / config_error
       → real_regression  確率 0.87   confidence 0.80

  B. 選択肢4つ  flaky_infra / real_regression / config_error / cannot_tell
       → cannot_tell      確率 1.00   confidence 0.99
```

A と B の違いは、`criteria` に1行足したことだけです。`state` も `instructions` も一字も変えていません。

```diff
 criteria={
     "flaky_infra":     "Infrastructure or test flakiness, not a code defect",
     "real_regression": "A code change broke behaviour that used to work",
     "config_error":    "A misconfiguration in the pipeline or environment",
+    "cannot_tell":     "The information given does not identify a cause",
 }
```

A は、材料がないまま `at_market` と `real_regression` を選び、しかも高い `confidence` を付けています。並べた選択肢の中での割れ方しか見ないので、材料がなくても、もっともらしい一つに確率が集まれば高く出るわけです。

一方 B は、選択肢を1つ足しただけで、同じ材料の乏しさを「判断できない」への確信として返してきます。ここが `confidence` の受け取り方の分かれ目になります。値の高低だけを見るのではなく、**どの選択肢に集まったのか**を見る。そのためには「判断できない」を選択肢に入れておく必要があります。

### 低い confidence が意味しないこと

![低い confidence の二つの型を cannot_tell で見分ける図。証拠が食い違う型は cannot_tell を選ばず 0.46 のまま割れ、材料不足の型は cannot_tell に確率 0.56 が移る](/images/jev-conf-low-two-types.png)

では低いほうはどうでしょうか。こちらも材料不足を意味しませんし、もう一度投げれば変わることも意味しません。Jev はほぼ決定論的で、同一入力を三回投げた実測ではばらつきが ±0.02 でした。リトライは空振りに終わります。

そして低い `confidence` には、二つの異なる状態が混ざっています。`state` の中で証拠が食い違っている場合と、判断に必要な材料がそもそも無い場合です。処理の仕方が正反対なので、区別しなければなりません。

区別する方法は、ここでも「判断できない」です。選択肢に入れて聞いたときに、モデルがそれを選ぶかどうかで分かれます。実測では、CI の矛盾したログ（アサーション失敗とフレーキー履歴が同居）は `cannot_tell` を用意していても選ばず、`real_regression` 0.46 のまま割れました。一方、監視のログ行は `cannot_tell` を足したとたん、そちらに確率 0.56 が移りました。

前者は証拠が揃っているので人が裁くしかありません。後者は `state` に足せる情報があるということなので、足せば解けます。それぞれの実測値は、このあとケース1とケース5で示します。

### 受け取ったら確かめる三つのこと

![答えを受け取ったら確かめる三つのことを順に並べた図。材料は足りているか、どの選択肢に集まったか、どれだけ集まったかの順に見る](/images/jev-conf-three-questions.png)

以上から、`confidence` を単体の閾値として受け取るのをやめ、チェックリストの形にします。

まず、質問を設計する時点で一度だけやっておくことが二つあります。

- 選択肢に「判断できない」を入れておく。
- 材料が足りているかを聞く Noul を、別に用意しておく。

そのうえで、答えが返ってくるたびに、次の順で確かめます。**順番が重要です。**

1. **材料は足りているか。** 用意しておいた Noul を見ます。低ければ、`confidence` がいくら高くても先へ進めません。`state` を足して投げ直すか、人に回します。
2. **どの選択肢に集まったか。** 「判断できない」に集まっているなら、それも材料不足の表明です。同じく `state` を足します。
3. **どれだけ集まったか。** ここでようやく `confidence` を見ます。低ければ、材料はあるのに答えが割れている状態なので、人に回します。

1 と 3 を逆にしないでください。`confidence` を先に見ると、材料が何もないのに高い確信が付いた答えが、そのまま自動処理に流れます。これがこの記事でいちばん危険な状態で、ケース3で実際の数値を見ます。

以下の五つのケースでは、この三つのうちどれかがそれぞれ主役になります。

## この原理を五つの具体的な活用場面で検討する

ここからは実際の場面です。以下の五つを例にとって説明していきます。ループエンジニアリングで判断を挟むことになる典型的な箇所です。

| | 場面 | その節で見る読み方 |
|---|---|---|
| ケース1 | CI 失敗の振り分け | 高い `confidence` が両端に出る |
| ケース2 | 社内イシューのトリアージ | 高い `confidence` は入力の質を保証しない |
| ケース3 | ループを続けるか人を呼ぶか | 高い `confidence` が最も危険な形で出る |
| ケース4 | レビュー指摘の採否 | `confidence` をそのまま閾値に使ってよい |
| ケース5 | ログ行の扱いを決める | 低い `confidence` の正体を見分ける |

どれも同じモデルの同じ返り値を扱います。違うのは、`confidence` のどの読み方が主役になるかです。

:::message alert
**本記事の数値は、すべてダミーデータに対する実測値です。**

CI ログ、社内イシュー、レビュー指摘、ログ行は、いずれも生成 AI にダミーデータとして作らせたものです。実運用のデータでは測っていません。生成 AI が書いた素材なので、実際のログやイシューより整っていて、判定しやすい側に寄っている可能性があります。

挙動の向き（選択肢の設計を変えると何が起きるか、材料を削ると何が起きるか）は再現するはずですが、**閾値の具体的な数字をそのまま持ち込むことはできません。** ご自身のデータで測り直してください。
:::

### ケース1　CI 失敗の振り分け

これは、マージ前の CI が落ちたときに、まず何をするかを決めるケースです。人手でやるなら、落ちたジョブのログを開き、テスト自体の不安定さなのかコードが壊れたのかを見て、もう一度回すか、直しに行くか、詳しい人を呼ぶかを決めているはずです。1日に何十回も出るので、最初の仕分けを機械に任せたくなります。

![CI 失敗の振り分け。入力の失敗ログから、cause の Choice、severity の Score、enough_info の Noul を経て、自動リトライ、自動修正、人に回す、ログを足して投げ直すの四つに分かれる](/images/jev-conf-case-ci.png)

- **入力**：失敗した CI ジョブのログと、変更のあったファイル。
- **聞くこと**：原因（Choice）、緊急度（Score）、材料の充足（Noul）。
- **出口**：自動でリトライ、自動修正を試す、人に回す、ログを足して投げ直す。
- **この節で見る読み方**：高い `confidence` が両端に出ます。値だけでは向きが分かりません。

質問は三つ、同じリクエストに入れます。

- Choice `cause`：`flaky_infra` / `real_regression` / `config_error` / `cannot_tell`
- Score `severity`：リトライで足りる / 数日中に直す / リリースを止める
- Noul `enough_info`：「与えられた情報で、どの変更がこの失敗を起こしたか特定できる」

まずは、ログをどこまで渡すかを変えて測ってみます。

| state | cause | confidence | enough_info |
|---|---|---|---|
| ログ全文（テスト名、アサーション差分、変更ファイル、ブランチ） | real_regression | 0.99 | 0.20 |
| テスト名のみ | cannot_tell | 0.78 | 0.06 |
| `CI failed.` のみ | cannot_tell | 0.99 | 0.04 |

一行目と三行目は、どちらも `confidence` 0.99 です。一方は原因を特定していて、もう一方は何も分かっていません。値だけで門を作ると、この二つが同じ扱いになります。見るべきは、その 0.99 が `real_regression` に付いたのか `cannot_tell` に付いたのかです。材料の減りを捉えているのは `enough_info` のほうで、0.20、0.06、0.04 と順に下がっています。

ところで、ここで効いてくるのが、コード側で済ませた比較を言葉にして渡すことです。失敗履歴はデータベースを引けば取れます。引いた結果を文章にして `state` に足してみます。

```
history: "This test passed on every run before commit 4f1a2c and has
          failed on every run since. That commit modified billing/invoice.py."
```

| state | cause | confidence | enough_info |
|---|---|---|---|
| ログ全文のみ | real_regression | 0.99 | 0.20 |
| ログ全文 + 上の履歴 | real_regression | 1.00 | **0.40** |

`enough_info` が倍になりました。回数や日時を数値のまま渡して比べさせるのではなく、比較した結果を文にして渡す。これが有効なことが数字で出ています。

さきほど予告した「低い `confidence` の一つ目の型」も、ここで観測できます。同じログ全文に、フレーキーさを示す履歴（「直近10回のうち2回失敗。10回すべて同じコミット上」）を足したセルでは、`cause` は `flaky_infra` に移らず `real_regression` のまま、`confidence` が 0.46 に落ちました。

このログにはアサーション失敗（`assert 0 == 1250`）が含まれていて、これはフレーキーさと矛盾する証拠です。`state` の中で証拠が食い違えば `confidence` が割れます。人に回す信号として使えます。

振り分けはこうなります。

| enough_info | confidence | 状態 | 処理 |
|---|---|---|---|
| 高 | 高 | 原因が特定できている | cause に応じて自動処理 |
| 高 | 低 | 材料はあるが証拠が食い違う | 人に回す |
| 低 | 高 | 材料がないまま答えている | 履歴と差分を足して再実行 |
| 低 | 低 | 何も言えていない | ログ収集そのものを疑う |

三行目と二行目で処理が正反対になっている点が要注意です。`confidence` だけを見ていると、この二つが区別できません。

### ケース2　社内イシューのトリアージ

これは、社内の問い合わせ窓口に上がってきた報告を、担当チームに渡すケースです。「経費精算の画面で申請ボタンが押せない」といった報告が、業務システムの数だけ別々の部署から届きます。読んで担当を決め、情報が足りなければ書き直しを頼む。この最初の仕分けが対象です。

![社内イシューのトリアージ。タイトルと本文から、team の Choice、urgency の Score、has_repro と enough_info の Noul を経て、自動割当、差し戻し、人が見るの三つに分かれる](/images/jev-conf-case-issue.png)

- **入力**：社内から上がってきたイシューのタイトルと本文。日本語のまま渡します。
- **聞くこと**：担当チーム（Choice）、緊急度（Score）、再現手順の有無と材料の充足（Noul 二つ）。
- **出口**：担当チームへ自動で割り当てる、書き直しを頼んで差し戻す、人が見る。
- **この節で見る読み方**：高い `confidence` は、入力の質を保証しません。

社外からの報告を対象にしないのは、`state` 経由の誘導という別の問題が絡み、本記事ではそれを測っていないためです。

日本語のまま投げて構いません。公式ドキュメントは英語が第一言語だと断っていますが、同じ判断を日英で測った実測ではほぼ一致しました（0.50 と 0.52）。トリアージ程度の粒度なら言語差は表面化しないようです。

質問は四つです。

- Choice `team`：`infra` / `app` / `account` / `cannot_tell`
- Score `urgency`：様子を見てよい / 今週中 / 即時
- Noul `has_repro`：「報告者以外が同じ現象を再現するのに足りる手順が書かれている」
- Noul `enough_info`：「この報告の内容だけで、どのチームが対応すべきか判断できる」

イシューの書かれ方を変えて測りました。

| イシュー | team | confidence | has_repro | enough_info |
|---|---|---|---|---|
| 手順、環境、期待と実際、影響範囲を記載 | app | 1.00 | 0.90 | 0.33 |
| 「申請ボタンが押せません。困っています」 | app | 0.90 | 0.06 | 0.24 |
| 「動きません」 | cannot_tell | 0.99 | 0.05 | 0.09 |
| 手順が途中で切れている | app | 0.98 | **0.25** | 0.22 |

ここで見ていただきたいのは二行目です。本文が一行しかないのに `team` は `app` を `confidence` 0.90 で返しています。担当の推測としては妥当で、実際 `app` で間違っていません。それでも、この報告をそのまま担当チームに流したら、担当者は何も調べられないでしょう。

`confidence` 0.90 が言っているのは「並べた四つの選択肢のうち `app` が抜けている」までです。報告が実装に着手できる質かどうかは、別の問いになります。

それを取っているのが `has_repro` です。完全な手順で 0.90、手順なしで 0.06、途中で切れた手順で 0.25。「手順:」という見出しの有無を拾っているだけなら四行目も高く出るはずなので、中身を見ていると考えられます。

振り分けはこうなります。

- `team` が `cannot_tell`：報告者に何の話か聞く。
- `has_repro` が低い：再現手順を書いてもらう差し戻し。`team` の答えは使わない。
- `has_repro` が高く `confidence` も高い：担当チームに自動で割り当てる。
- `has_repro` が高く `confidence` が低い：担当が割れている。人が見る。

なお `has_repro` と `enough_info` は別々の Noul なので、足して 1 になることを期待しないでください。前述のとおり、Noul どうしは補完関係にありません。

### ケース3　ループを続けるか人を呼ぶか

これは、エージェントにテストを直させている最中に、そのまま走らせ続けてよいかを判断するケースです。放っておくと、同じ修正を何度も試して時間とトークンを溶かします。かといって一手ごとに確認を求めるなら、自走させる意味がありません。

![ループ制御。試行履歴から、next の Choice と enough_info の Noul を経て、続行、人に聞く、諦めて報告するの三つに分かれる](/images/jev-conf-case-loop.png)

- **入力**：自走中のエージェントが記録した試行履歴（何を変えて、結果がどうだったか）。
- **聞くこと**：次の一手（Choice）、材料の充足（Noul）。
- **出口**：そのまま続行、人に聞く、諦めて報告する。
- **この節で見る読み方**：高い `confidence` が最も危険な形で出る場所です。

二つの信号を分ける必要が、ここで最もはっきり出ます。

- Choice `next`：`continue` / `ask_human` / `stop`
- Noul `enough_info`：「記録された試行に、成功しそうな次の手を選ぶのに足りる情報がある」

`state` には試行履歴を入れて測りました。

| 試行履歴 | next | confidence | enough_info |
|---|---|---|---|
| 3回試し、3回目で原因を特定（呼び出し側が引数を設定していない） | continue | 0.97 | 0.65 |
| 1回試して「まだ失敗」だけ | **continue** | **0.93** | **0.14** |
| 同じ修正を5回繰り返し、毎回同じ失敗 | continue | 0.17 | 0.13 |

二行目が危険な状態です。試行が一度きりで、結果も「まだ失敗」としか記録されていないのに、`continue` を `confidence` 0.93 で返します。一行目の 0.97 とほとんど変わりません。一方 `enough_info` は 0.14 で、一行目の 0.65 と明確に離れています。材料の不足を捉えているのはこちらです。

三行目は性質が違います。`enough_info` は同じく低いのですが、`confidence` が 0.17 まで落ちています。`continue`、`ask_human`、`stop` に確率が散っている状態で、次の手が決まらないことを示しています。

以上から、門はこう置くことになります。

```python
if r.nouls["enough_info"].noul < 0.3:
    ask_human(reason="証拠が足りない")      # 二行目と三行目を両方捕まえる
elif r.choices["next"].confidence < 0.5:
    ask_human(reason="次の手が決まらない")
else:
    dispatch(r.choices["next"].choice)
```

順序が肝心です。`enough_info` を先に見ます。`confidence` を先に見ると、二行目（0.93）が素通りしてしまいます。

### ケース4　レビュー指摘の採否

これは、自動レビューが出した指摘を、そのまま直すか人が見るかに振り分けるケースです。自動レビューを回すと、明らかに直してよいものから好みの問題まで、質の違う指摘が混ざって出てきます。全部人が見ると自動化の意味が薄れ、全部自動で直すと事故が起きます。

![レビュー指摘の採否。差分と指摘から、disposition の Choice と grounded の Noul を経て、自動修正、人の確認、棄却の三つに分かれる](/images/jev-conf-case-review.png)

- **入力**：差分と、自動レビューが出した指摘一件。
- **聞くこと**：処理の仕方（Choice）、指摘がコードに裏づけられているか（Noul）。
- **出口**：自動修正、人の確認、棄却。
- **この節で見る読み方**：`confidence` をそのまま閾値に使ってよい場合です。

ここまで注意点ばかりでしたが、`confidence` が素直に効く例も見ておきましょう。冒頭のコード例と同じ構成です。

- Choice `disposition`：`auto_fix` / `human_review` / `dismiss`
- Noul `grounded`：「その指摘は、示された差分のコードによって裏づけられている」

性質の違う指摘を三つ投げました。

| 指摘 | disposition | confidence | grounded |
|---|---|---|---|
| 未使用の変数がある。削除せよ | auto_fix | 0.93 | 0.98 |
| 関数名を他と揃えるべきだ | human_review | 0.15 | 0.17 |
| `decimal.Decimal` の精度を設定していない（差分に該当箇所なし） | dismiss | 0.87 | **0.02** |

ここでは `confidence` が期待どおりに働いています。明白な指摘に 0.93、議論の余地がある指摘に 0.15。三つの選択肢はどれも実質的な処理を指していて、材料（差分と指摘文）も常に揃っています。選択肢の集合が妥当で材料も揃っているとき、`confidence` は素直に読めるわけです。

ただし、誤検知だけは `confidence` では捕まりません。三行目は `dismiss` に 0.87 と高い値が付いていますが、これは「棄却すべきだと確信している」であって、指摘が誤りかどうかの判定ではありません。それを取っているのが `grounded` で、0.02 を返しています。`grounded` が低ければ `disposition` の値によらず棄却でよい、という使い方になります。

もう一点、二行目についても補足しておきます。`human_review` に 0.15 という低い値が付いたので「人が決めるべき案件だ」と読みたくなりますが、`cannot_tell` を足して測り直すと `cannot_tell` が確率 0.41 で最有力になり、`human_review` は 0.32 に下がりました。このプロジェクトの命名規約が `state` に書かれていないので、判断材料が無いというのが正確な読みです。つまりこれは「人が決めるべき案件」ではなく、「規約を `state` に入れれば決まる案件」でした。

### ケース5　ログ行の扱いを決める

これは、本番ログに流れてきた1行を見て、夜中に人を起こすかどうかを決めるケースです。条件をルールで書き下すと、サービスが増えるたびに書き足すことになり、誤報と見逃しの調整が終わりません。

![ログ監視。ログ一行から action の Choice を経て、無視、チケット起票、即時呼び出しの三つに分かれる](/images/jev-conf-case-monitor.png)

- **入力**：監視対象のログ一行。
- **聞くこと**：どうするか（3択）。
- **出口**：無視、チケット起票、即時呼び出し。
- **この節で見る読み方**：低い `confidence` の正体を、`cannot_tell` で見分けます。

ケース1で予告した「低い `confidence` のもう一つの型」を、ここで確認します。

| ログ行 | action | confidence |
|---|---|---|
| `retry 3/3 failed for charge ch_9f21: upstream returned 503`（1回目） | ticket | 0.27 |
| 同上（2回目） | ticket | 0.31 |
| 同上（3回目） | ticket | 0.29 |
| `retry 1/3 for charge ch_9f21: upstream 503` | ignore | 0.30 |
| `all retries failed for 4182 charges in the last 5 minutes` | page | 0.99 |

上の三行は、同じ行を三回投げて 0.27、0.31、0.29 と低いまま安定しています。ここで筆者は「一件の課金失敗を起票すべきかはモデルが決められる問題ではない。サービスの重要度も当直の人数も `state` に書かれていないのだから、閾値は人間が決めるしかない」と結論しかけました。

しかし、この3択には `cannot_tell` が入っていません。記事の前半で自分が書いたことを、自分で適用していなかったわけです。足して測り直しました。

| 選択肢 | 答え | confidence |
|---|---|---|
| 3つ（ignore / ticket / page） | ticket | 0.27 |
| 4つ（+ cannot_tell）1回目 | **cannot_tell**（確率 0.56） | 0.41 |
| 4つ（+ cannot_tell）2回目 | **cannot_tell**（確率 0.55） | 0.40 |

`cannot_tell` が最有力になりました。つまりこれは「本質的に割れる案件」ではなく、**材料不足**だったのです。サービスの重要度と当直方針を `state` に書けば、モデルは答えられる見込みがあります。低い `confidence` を見て「ここは人間が決める領域だ」と解釈したのは、こちらの早合点でした。

一方、ケース1の矛盾したログは、`cannot_tell` を用意していても選びませんでした。証拠が揃っていて解釈だけが割れている状態は、`cannot_tell` では吸収されません。**この二つを見分けられることが、`cannot_tell` を置くもう一つの効用です。**

なお、決定論的に近いので同じログ行でアラートがばたつくことはなく、監視ではこれが利点になります。最終行のように規模が桁違いになれば `confidence` 0.99 が返るので、その帯だけを自動で page に回せば済みます。

## 受け取り方のまとめ

五つの事例で見た読み方を、観測から処理への対応として並べ直します。

### 観測から処理への対応表

![confidence と enough_info の二軸で作った 2x2 のマップ。右下の「材料なしで断言」の区画だけが着色され、最も危険な状態として示されている](/images/jev-conf-summary-map.png)

| 観測 | 読み方 | 処理 |
|---|---|---|
| 高い。実質的な選択肢に集中 | 並べた選択肢の中で一つが抜けている | 材料の充足を別途確認したうえで自動処理 |
| 高い。`cannot_tell` に集中 | 材料がない | `state` を足して投げ直す |
| 高い。`cannot_tell` を用意していない | 何も分からない。最も危険 | 選択肢の設計をやり直す |
| 低い。`cannot_tell` を出しても選ばない | 証拠は揃っていて解釈が割れている | 人に回す |
| 低い。`cannot_tell` を出すとそれが勝つ | 判断材料そのものが無い | `state` を足して投げ直す |

この表の三行目と、ケース3の二行目（`continue` 0.93 に対し `enough_info` 0.14）は同じ状態です。`confidence` だけを見ていると、最も危険な状態が最も安全な状態と同じ顔をして現れます。

`state` の作り方についても一点だけ。履歴を引くのも前回との差を取るのもコードのほうが正確で、比較した結果を文にして `state` に足すと、CI のケースで `enough_info` が 0.20 から 0.40 に上がりました。数値を並べて引き算をさせるのではなく、引き算の結果を渡します。

```python
# 数値を並べて、差を取らせている
state = {"ビルド時間": 420, "直近平均": 180}

# 比較はコードで済ませ、結果を言葉で渡す
state = {"ビルド時間の傾向": "直近平均の 2.3 倍に増えている"}
```

### cannot_tell は常に入れるべきか

選択肢を1つ増やすことに副作用はないのでしょうか。材料が十分にあるケースで、選択肢だけを変えて測りました。

| 入力 | 選択肢 | 答え | その確率 | confidence |
|---|---|---|---|---|
| 明白なレビュー指摘（未使用変数） | 3つ | auto_fix | 0.95 | 0.92 |
| 同上 | 4つ（+ `cannot_tell`） | auto_fix | 0.86 | **0.82** |
| CI のログ全文 | 4つ（+ `cannot_tell`） | real_regression | 0.99 | 0.99 |
| 同上 | 3つ | real_regression | 1.00 | 1.00 |

答えは変わりませんでした。`cannot_tell` が取った確率は 0.02 と 0.01 で、材料が足りているときは実質的に無視されます。さきほど監視やレビューで `cannot_tell` が最有力になったのは、選択肢が答えを奪ったのではなく、本当に材料が足りていなかったからだと分かります。

一方で `confidence` の値は動きます。これは分布が鈍ったのではなく、**選択肢の数が変わると目盛りそのものが変わる**ためです。式に `n` が入っているからで、3択の `(3 × 0.95 − 1) / 2 = 0.925` と4択の `(4 × 0.86 − 1) / 3 = 0.813` は、どちらも返り値と一致します。

以上をまとめると、こうなります。

| | 内容 | 根拠 |
|---|---|---|
| 利点 | 材料不足が、根拠のない答えへの高い確信ではなく「判断できない」への確信として返る | `at_market` 0.93 が `cannot_tell` 1.00 に変わった |
| 利点 | 低い `confidence` の原因を見分けられる | 監視は `cannot_tell` 0.56、CI の矛盾は選ばず 0.46 のまま |
| 副作用 | 材料が十分なら、ほぼ確率を取らない。答えは変わらない | 取った確率は 0.02 と 0.01 |
| 副作用 | 選択肢が増えるぶん `confidence` の目盛りが下がる | 同じ答えで 0.92 から 0.82 へ |
| 条件 | `cannot_tell` が返ったときに何を足すかを先に決めておく | 足せる当てがなければ、人に回すための遠回りにしかならない |
| 条件 | 閾値は選択肢の数ごとに測り直す | 3択の 0.9 を4択に持ち込むと、通るはずのものが止まる |

条件の二つが満たせるなら、入れて構いません。なお Score も事情は同じで、段階の刻み方を変えると水準が動きます（同じ判断が3段階で 0.44、6段階で 0.62 でした）。

### 閾値を較正したらバージョンを固定する

`jev-latest` は新しいリリースが出ると指す先が動きます。ドキュメントも、特定のバージョンで `confidence` の閾値を調整したなら、エイリアスではなくバージョン ID（`jev-1.13.0`）を指定し、移行は自分のスケジュールで行うように書いています。ここまで見てきたとおり、`confidence` は選択肢の数を変えるだけでも水準が動く値なので、モデルが入れ替われば当然動きます。

レスポンスの `model` フィールドには、実際に答えたバージョン ID が入ります。判定を記録に残すなら、これも一緒に残しておきます。あとから閾値が合わなくなったときに、モデルが変わったのか `state` が変わったのかを切り分けられます。

### 測っていないこと

最後に、この記事が測っていない範囲をまとめておきます。

入力がすべてダミーデータである点は冒頭に書いたとおりです。加えて、各セルは表現を一通りしか試していません。質問文を書き換えれば値は動きます。

Score の `confidence` の計算式は同定できていません。段階数が増えるほど開示式からずれることは分かりましたが、その差を説明する式は見つかっていません。

数値の桁が判断に影響する現象は、別のドメイン（架空の通貨）では大きく出ました。購買力を固定して桁だけ 1 万倍したところ、確率が 0.61 から 0.28 まで動きました。一方 CI ログの単位表記（`30 s` と `30000 ms`、`3.8 GB` と `4080218931 bytes`）では、差は 0.06 以下にとどまりました。CI の表記差については、影響が小さかったとしか言えません。

ドキュメントが挙げている失敗モードのうち、`state` が大きくなるほど精度が落ちる現象と、`state` に混入した誘導的な記述の影響は、本記事では測っていません。

## おわりに

`confidence` という名前は、人間が「自信」という言葉から連想するものと、実際に計算されている量とのあいだに距離があります。実際に計算されているのは分布の尖り具合であって、モデルが「どれだけ確かな根拠を持っているか」ではありません。この距離に気付かないまま閾値を置くと、材料が何もない判断が、最も自信のある判断として自動処理に流れていきます。

筆者自身、最初は逆の予測を立てていました。`state` から情報を削れば confidence が下がるはずだ、と。測ったら上がりました。理由は後から考えれば当たり前で、情報が増えるほど「そうとも言えるが、こうとも言える」という材料が増えて確率が割れるからです。情報が減れば、割れる理由も一緒に消えます。

救いは、対策が閾値のチューニングではなく、**選択肢の設計**という、設計時に一度やれば済む作業だったことです。「判断できない」という出口を用意しておけば、材料不足はそこに集まります。あとは材料の充足を別の Noul で聞いて、`confidence` より先に見る。

ループエンジニアリングで最初に決めるのは閾値だと思っていましたが、実際に効いたのは、モデルに「答えない」という出口を与えるかどうかでした。型のついた答えは扱いやすい代わりに、返ってきた数値を無条件に信じたくなります。何を意味しているかは、ドキュメントを読み、手元のデータで測ってから決めるのがよさそうです。
