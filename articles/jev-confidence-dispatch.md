## はじめに

エージェントを回していると、判断を挟みたい箇所が増えます。CI が落ちたとき、リトライするのか、自動修正を試すのか、人を呼ぶのか。社内から上がってきたイシューを、どのチームに渡すのか、書き直しを頼むのか。

エージェントを回し続けるには、ループのどこで判断を挟み、どこで人間に渡すかを決めなければなりません。本記事ではこれを**ループエンジニアリング**と呼びます。自動で進めてよい場面、情報を足して投げ直すべき場面、人を呼ぶべき場面を、コードが区別できる形にする作業です。

こうした振り分けに、[Jev](https://docs.typesafe.ai/) のような「文章を返さず、型のついた答えと確率を返すモデル」が使えます。そして使い始めると、たいてい `confidence`（確信度と訳される値）に閾値を置くところから設計が始まります。高ければ自動で処理し、低ければ人に回す。[公式ドキュメント](https://docs.typesafe.ai/confidence#three-paths-for-using-confidence-in-your-code)もその三分割を勧めていますし、実際うまくいく場面もあります。

ところが、高い `confidence` が何を保証しているのかは、思ったより狭いのです。筆者は「材料が足りないときは confidence が下がるはずだ」と思い込んで実験を組み、**予測と正反対の結果**を得ました。Choice で聞いた系列では、情報を削るほど confidence が上がったのです。

この記事は、その実測と理由の解説、そして利用方法の提案です。CI 失敗の振り分け、社内イシューのトリアージ、エージェントのループ制御、レビュー指摘の採否、ログ監視の五つを、それぞれ `confidence` の違う読み方の事例として並べます。数値はすべて実際に測ったものです。ただし振り分けの提案には、少数の実測から推した部分が含まれます。どこまでが観測でどこからが推論かは、本文で分けて書きます。

## TL;DR

- `confidence` は **`probabilities` から計算される統計量**で、第二の独立した指標ではありません。測っているのは **こちらが並べた選択肢の中での、答えの割れ方** だけです。材料が足りているかも、答えが正しいかも測っていません（[開示されている3択向けの近似式](https://docs.typesafe.ai/confidence#confidence-is-derived-from-the-probabilities)と、実測値は表示精度の範囲で一致しました）。
- **材料不足は、低い confidence ではなく「根拠のない答えへの高い confidence」として現れることがあります。** 同じ `state` に同じ質問を投げ、選択肢だけを変えた対照実験の2例で確認しました。
- 対策は閾値の調整ではなく、**選択肢に「判断できない」を入れ、材料の足り具合を別の Noul で取ること**です。前者を入れると、同じ材料不足が `cannot_tell`（判断できない）1.00 として返るようになりました（2例）。後者を省いて `confidence` だけで門を作ると、材料のないまま高い確信が付いた答えが素通りします。ただし、この対策で誤った自動処理がどれだけ減るかは測っていません。
- 低い confidence には、**候補が拮抗している場合**と**材料が無い場合**が混ざりえます（同時にも起きます）。`cannot_tell` を入れて聞き直すと手がかりになりましたが、少数例での観測で、二つを確実に見分ける方法ではありません。なお同じ入力を三回送っても答えは変わりませんでした。
- **閾値は文脈をまたいで持ち込めません。** 選択肢の数、Score の段階数、質問文、言語のどれかが変われば、同じ 0.9 が別の状態を指します。
- **指示は日本語のままで始めて構いません。** 正解ラベル付きの20件では日本語 20/20、英語 19/20 で、日本語での低下は観測されませんでした（20件なので、同等とまでは言えません）。ただし Score の値は言語で最大 0.54 動いたので、Score の閾値は実際に使う言語で測り直します。
- 以上を、CI 失敗の振り分け・社内イシューのトリアージ・ループ制御・レビュー指摘の採否・ログ監視の**五つの場面**で、それぞれ違う読み方の事例として測りました。

| | 場面 | 実測で分かったこと |
|---|---|---|
| ケース1 | CI 失敗の振り分け | 原因を特定できた state と、ログが空の state が、どちらも confidence 0.99。値だけでは向きが分からない |
| ケース2 | 社内イシューのトリアージ | 本文が一行の報告でも担当チームを 0.90 で当てる。報告の質は別の Noul でしか分からない |
| ケース3 | ループを続けるか人を呼ぶか | 試行1回だけの履歴で `continue` を 0.93。同じ state で `enough_info` は 0.14 |
| ケース4 | レビュー指摘の採否 | 明白な指摘 0.93、議論の余地あり 0.15。この3件では confidence の高低が指摘の性質と対応した |
| ケース5 | ログ行の扱いを決める | 三回投げて 0.27／0.31／0.29 と低いまま安定。`cannot_tell` を足すとそちらへ 0.56 が移った |

## Jev の呼び出しと confidence の定義

まずは Jev がどういうモデルで、`confidence` がどう計算されているかを押さえます。この節の内容が、以降のすべての判断の土台になります。

### Jev に何を渡して何が返るか

![Jev の呼び出し構造。左に判断材料を入れる state と、Choice / Score / Noul を並べる questions があり、それが jev-1.13 に入って、右に choice、confidence、noul という型のついた answers が返る](/images/jev-conf-io.png)

Jev は文章を生成しません。判断材料（[`state`](https://docs.typesafe.ai/concepts/state)）と、型のついた問い（[`questions`](https://docs.typesafe.ai/primitives)）を渡すと、こちらが定義した答えの集合の中から選んで返します。コードがそのまま `if` で分岐できる値が返ってくる、と考えてください。

まずは実際のリクエストと返り値を見てみましょう。自動レビューの指摘を処理する例です。

```python
from typesafe_sdk import TypeSafeClient, Choice, Noul

with TypeSafeClient() as client:
    r = client.system_one(
        state={
            "diff": "+def compute_refund(amount, proration_days):\n"
                    "+    unused = amount * 0\n"
                    "+    return round(amount * proration_days / 30)\n",
            "finding": "`unused` is assigned but never read. Remove it.",
        },
        questions={
            "disposition": Choice(
                instructions="How should this automated review finding be handled?",
                criteria={
                    "auto_fix": "Apply the suggested change without a person looking at it",
                    "human_review": "A person should decide before anything changes",
                    "dismiss": "The finding is not correct or not worth acting on",
                },
            ),
            "grounded": Noul(
                instructions="The finding is supported by the code shown in the diff."
            ),
        },
    )

r.choices["disposition"].choice       # "auto_fix"
r.choices["disposition"].confidence   # 0.93
r.nouls["grounded"].noul              # 0.98
```

ここで一つ、後で効いてくる性質があります。`questions` に並べた問いは、同じ `state` に対してまとめて評価されます。一回のリクエストで複数の答えを取れるので、この記事で繰り返し出てくる「答えと、その答えを信用してよいかを別々に聞く」という設計が、追加のリクエストなしで実現できます。

### 質問の三つのタイプ

| | 何を判定するか | 答えの形 |
|---|---|---|
| [Choice](https://docs.typesafe.ai/primitives/choice) | 順序のないカテゴリへの分類 | 定義した選択肢から一つ。各選択肢の確率と `confidence` が付く |
| [Score](https://docs.typesafe.ai/primitives/score) | 順序のある量の分類 | 定義した段階（「様子見でよい」「今週中」「即時」など）のどこに位置するか。確率と `confidence` が付く |
| [Noul](https://docs.typesafe.ai/primitives/noul) | 命題の確からしさの判定 | yes / no ではなく、no らしさから yes らしさまでの連続量（0〜1）。`confidence` は付かない |

型は、判定したいものに順序があるかどうかで決まります。担当チーム（`infra` / `app` / `account`）を Score で聞くと、期待値 1.5 が「`app` と `account` のあいだ」という無意味な値になります。逆に緊急度を Choice で聞くと、「今週中」と「即時」に割れている状態と、「様子見」と「即時」に割れている状態が、同じ「割れている」として扱われます。後者のほうが危ういのに区別が付きません。

### confidence は分布の尖り具合

![3択の確率分布を2つ並べた棒グラフ。確率が一つに集中した 0.07/0.92/0.01 は confidence 0.88、散らばった 0.60/0.04/0.36 は confidence 0.40 になる](/images/jev-conf-confidence-shape.png)

ここからが本題です。`confidence` は第二の独立した指標ではありません。`probabilities` から計算される統計量です。

[公式ドキュメント](https://docs.typesafe.ai/confidence#confidence-is-derived-from-the-probabilities)が、3択のデモの中で計算式を示しています（`(3 × largest probability − 1) / 2`（仮訳: (3 × 最大の確率 − 1) / 2）を近似として使う、と書かれています。2026年9月23日確認）。実測値と突き合わせてみました。

| Choice の probabilities | 返り値 confidence | 開示式 |
|---|---|---|
| [0.60, 0.04, 0.36] | 0.400 | 0.400 |
| [0.07, 0.92, 0.01] | 0.880 | 0.880 |
| [0.00, 1.00, 0.00] | 1.000 | 1.000 |

表示精度の範囲で一致しました。確率が一つの選択肢に集まれば高く、散らばれば低い、という数字です。なお開示されているのはデモ用の3択の近似式で、API の計算仕様そのものとして示されているわけではありません。4択でも同じ形で近い値になりましたが（差は最大 0.01 程度）、これは実測からの当てはめです。

:::message
**式の意味をかみくだくと**

選択肢が3つあるとき、いちばん迷っている状態は「どれも同じくらい」、つまり3つとも 33%（= 1/3）です。逆にいちばん迷っていない状態は、どれか1つが 100% です。

`confidence` は、この2つを 0 と 1 に決めておいて、**いま一番大きい確率がそのあいだのどこにいるか**を測っているだけの数字です。

- 一番大きい確率が 1/3（33%）のとき → confidence は 0
- 一番大きい確率が 1（100%）のとき → confidence は 1

式 `(n × peak − 1) / (n − 1)` の `peak` が「一番大きい確率」、`n` が「選択肢の数」です。3択なら `(3 × peak − 1) / 2` になります。上の表の2行目で確かめてみましょう。一番大きい確率は 0.92 なので、

```
(3 × 0.92 − 1) / 2 = (2.76 − 1) / 2 = 1.76 / 2 = 0.88
```

表の confidence 0.880 と同じ値になりました。1行目も `(3 × 0.60 − 1) / 2 = 0.40` です。選択肢が4つなら、割る数が 2 ではなく 3 になります。

ここで大事なのは、**この式に出てくるのが確率の数字だけ**ということです。`state` に何が書いてあったか、答えが当たっていたか、判断材料が十分だったか。そういったものは式のどこにも入っていません。もちろん確率そのものは `state` から計算されるので、`confidence` が正しさと無関係だとまでは言えません。ただ、`confidence` は正解の確率そのものでも、材料が足りているかを独立に調べた結果でもありません。正解率とどう関係するかは、自分のタスクで別に確かめる必要があります。
:::

ここから二つのことが出てきます。第一に、`confidence` が測っているのは**こちらが並べた選択肢の中での、答えの割れ方**です。判断材料が足りているかどうかも、答えが正しいかどうかも測っていません。第二に、`confidence` は `probabilities` の関数なので、確率と独立に動くことはありません。「確率は割れているが確信はある」という状態は、構成上つくれないのです。

### Choice、Score、Noul それぞれの confidence 値

三つの型はどれも、内側では選択肢や段階に対する確率分布を返しています。`confidence` はその分布を要約した数字で、意味は共通です。ただし**型をまたいで同じ数字として扱うことはできません**。

| | 返るもの | confidence | 再現 | 注意 |
|---|---|---|---|---|
| Choice | 選んだ選択肢と、各選択肢の確率 | あり | 開示式に近い値（3択と4択の実測、表示精度の範囲） | 選択肢の数が変わると目盛りも変わる |
| Score | score（期待値）と、各段階の確率 | あり | 3段階では開示式に近い値。段階が増えるほど返り値のほうが高くなる傾向 | `score` も `confidence` も段階数に依存する。段階の説明文を訳すとずれる。Choice とも互換ではない |
| Noul | noul（yes である確率、0〜1）だけ | なし | `2 × noul − 1` の絶対値で作れる | 0.5 は「中くらい」ではなく「どちらとも言えない」 |

[ドキュメント](https://docs.typesafe.ai/confidence)は、`confidence` は便利な既定値として提供しているだけでこの定義に縛られる必要はない、だから `probabilities` を丸ごと返しているのだ、と書いています。用途に合わないと感じたら、上位2つの差やエントロピーなど、`probabilities` から自分で別の尺度を作って使えます。

Noul にはもう一点あります。[ドキュメント](https://docs.typesafe.ai/model-jaggedness/jev-1.13#common-sense-structural-invariants)によれば、ある命題とその否定を別々に聞いたときに確率が整合する（足して 1 になる）ことは保証されていません。確率を足して検算する使い方はできないということです。なお筆者の実測で「不当に安い」0.07 と「妥当である」0.05 が両立した例がありますが、この二つは否定の関係ではない（高すぎる報酬なら両方とも偽）ので、上の性質の裏づけにはなりません。

:::message
**Noul と Score の違い**

どちらも連続量を返すので似て見えますが、中間の値が意味するものが違います。

Noul には「程度」の軸がありません。「この依頼は危険である」を Noul で聞いて 0.5 が返っても、中くらい危険という意味にはなりません。危険かどうか判断が割れている、という意味です。強度が欲しいなら、段階を定義して Score で聞く必要があります。

逆に Score の中間値は曖昧です。5段階で 2.0 が返ったとき、「段階2に集中している」のか「0と4に割れた結果たまたま中央に来た」のかが、期待値からは分かりません。だから `probabilities` か `confidence` を併せて見ることになります。

**Noul の連続量は確からしさ、Score の連続量は程度と確からしさの混合です。**
:::

## confidence が答えていないこと

計算方法が分かると、この数値が答えていない問いも決まります。判断材料が足りているかどうかが、それにあたります。ここでは高い場合と低い場合を順に見ていきます。

### 高い confidence が意味しないこと

![同一の state から選択肢集合だけを分岐させた対照実験の図。cannot_tell なしでは real_regression に confidence 0.80、cannot_tell ありでは cannot_tell に confidence 0.99 が返る](/images/jev-conf-cannot-tell-ab.png)

まずは高いほうからです。高い `confidence` は、材料が足りていることを意味しません。

想定しているのは、求人情報が次々に流れてくるパイプラインです。一件ずつ「提示額は相場と比べてどうか」を判定し、安すぎるものに印をつけていく、といった処理を考えてください。たいていの求人票には職種も勤務地も書かれていますが、取り込みに失敗したり記載が抜けていたりする一件が、ときどき混ざります。**その欠けた一件が来たときに何が起きるか**が、ここでの問題です。

これを確かめるために、同じ `state` に同じ質問文を投げ、選択肢だけを変えて測りました。

```
state: {"offer": "$150,000 per year"}     ← 職種も勤務地も書かれていない
質問:  この提示額は相場と比べてどうか

  A. 選択肢3つ  below_market（相場より低い）/ at_market（相場並み）/ above_market（相場より高い）
       → at_market      確率 0.93   confidence 0.89

  B. 選択肢4つ  上の3つ + cannot_tell（判断できない）
       → cannot_tell    確率 1.00   confidence 1.00
```

```
state: {"job": "unit-tests", "log": "CI failed."}     ← ログ本体がない
質問:  この CI 失敗の原因として最も確からしいものはどれか

  A. 選択肢3つ  flaky_infra（環境やテストの不安定さ）/ real_regression（コードの退行）/ config_error（設定の誤り）
       → real_regression  確率 0.87   confidence 0.80

  B. 選択肢4つ  上の3つ + cannot_tell（判断できない）
       → cannot_tell      確率 1.00   confidence 0.99
```

A と B の違いは、`criteria` に1行足したことだけです。`state` も `instructions` も一字も変えていません。

```diff
 criteria={
     "flaky_infra":     "Infrastructure or test flakiness, not a code defect",
     "real_regression": "A code change broke behaviour that used to work",
     "config_error":    "A misconfiguration in the pipeline or environment",
+    "cannot_tell":     "The information given does not identify a cause",
 }
```

A は、材料がないまま `at_market` と `real_regression` を選び、しかも高い `confidence` を付けています。並べた選択肢の中での割れ方しか見ないので、材料がなくても、もっともらしい一つに確率が集まれば高く出るわけです。

一方 B は、選択肢を1つ足しただけで、同じ材料の乏しさを「判断できない」への確信として返してきます。ここが `confidence` の受け取り方の分かれ目になります。値の高低だけを見るのではなく、**どの選択肢に集まったのか**を見る。そのためには「判断できない」を選択肢に入れておく必要があります。

### 低い confidence が意味しないこと

では低いほうはどうでしょうか。こちらも材料不足を意味しませんし、もう一度投げれば変わることも意味しません。同一入力を三回投げた実測では、ばらつきは ±0.02 で答えも変わりませんでした。同じ入力を送り直して不確実性が解消される、と期待できる根拠は得られていません。ただし小さな揺れでも閾値の近くでは判定が入れ替わりうるので、閾値の際に来る値は揺れを前提に扱ってください。

そして低い `confidence` には、少なくとも二つの異なる状態が混ざりえます。複数の原因が同じくらいもっともらしい場合と、判断に必要な材料がそもそも無い場合です。両方が同時に起きることもあります。

![低い confidence の二つの型を cannot_tell の選ばれ方から推す図。候補が拮抗している型は cannot_tell を選ばず 0.51 対 0.48 のまま割れ、材料不足の型は cannot_tell に確率 0.56 が移る](/images/jev-conf-low-two-types.png)

手がかりになるのが、ここでも「判断できない」です。実測では、回帰ともフレーキーとも読める CI の履歴は `cannot_tell` を用意していても選ばず、`real_regression` 0.51 と `flaky_infra` 0.48 が拮抗しました（`confidence` 0.35）。一方、監視のログ行は `cannot_tell` を足すと、そちらに確率 0.56 が移りました。

ただし二点、留保があります。監視の例で足した `cannot_tell` の説明文には「サービスの重要度や当直方針が書かれていない」と、足りない情報を具体的に書いていました。汎用的な「判断できない」でも同じ結果になるかは確かめていません。また CI の例でも `enough_info` は 0.16 と低く、`cannot_tell` を選ばなかったことは材料が十分だという証明になりません。

ここから立てられるのは、`cannot_tell` を選ばずに割れたなら人に回し、`cannot_tell` が最有力になったなら `state` に何を足せるかを検討する、という作業仮説です。足せば実際に解けるかは、情報を足して測り直すまで分かりません。それぞれの実測値は、このあとケース1とケース5で示します。

### 受け取ったら確かめる三つのこと

以上から、`confidence` を単体の閾値として受け取るのをやめ、チェックリストの形にします。

まず、質問を設計する時点で一度だけやっておくことが二つあります。

- 選択肢に「判断できない」を入れておく。
- 材料が足りているかを聞く Noul を、別に用意しておく。

![答えを受け取ったら確かめる三つのことを並べた図。材料は足りているか、どの選択肢に集まったか、どれだけ集まったかの三つを見る](/images/jev-conf-three-questions.png)

そのうえで、答えが返ってくるたびに、次の三つを確かめます。

1. **材料は足りているか。** 用意しておいた Noul を見ます。低ければ、`confidence` がいくら高くても先へ進めません。`state` を足して投げ直すか、人に回します。
2. **どの選択肢に集まったか。** 「判断できない」に集まっているなら、それも材料不足の表明です。同じく `state` を足します。
3. **どれだけ集まったか。** ここでようやく `confidence` を見ます。低ければ、材料はあるのに答えが割れている状態なので、人に回します。

三つとも見るのであれば、順番はどれからでも構いません。自動処理に流れる案件は同じになります。変わるのは、人に回したときに記録される理由だけです（この理由が、あとで何を直すかの手がかりになります）。

重要なのは **1 を省かないこと**です。`confidence` だけで門を作ると、材料が何もないのに高い確信が付いた答えが、そのまま自動処理に流れます。この記事で最も避けたい状態で、ケース3で実際の数値を見ます。

以下の五つのケースでは、この三つのうちどれかがそれぞれ主役になります。

## この原理を五つの具体的な活用場面で検討する

ここからは実際の場面です。以下の五つを例にとって説明していきます。ループエンジニアリングで判断を挟むことになる典型的な箇所です。

| | 場面 | その節で見る読み方 |
|---|---|---|
| ケース1 | CI 失敗の振り分け | 高い `confidence` が両端に出る |
| ケース2 | 社内イシューのトリアージ | 高い `confidence` は入力の質を保証しない |
| ケース3 | ループを続けるか人を呼ぶか | 材料が乏しいまま高い `confidence` が出る |
| ケース4 | レビュー指摘の採否 | `confidence` をそのまま閾値に使ってよい |
| ケース5 | ログ行の扱いを決める | 低い `confidence` の正体を見分ける |

どれも同じモデルの同じ返り値を扱います。違うのは、`confidence` のどの読み方が主役になるかです。

:::message alert
**本記事の数値は、すべてダミーデータに対する実測値です。**

CI ログ、社内イシュー、レビュー指摘、ログ行は、いずれも生成 AI にダミーデータとして作らせたものです。実運用のデータでは測っていません。生成 AI が書いた素材なので、実際のログやイシューより整っていて、判定しやすい側に寄っている可能性があります。

挙動の向き（選択肢の設計を変えると何が起きるか、材料を削ると何が起きるか）も少数の例での観測で、他のデータで再現するかは分かりません。**閾値の具体的な数字は、なおさらそのまま持ち込めません。** ご自身のデータで測り直してください。
:::

### ケース1　CI 失敗の振り分け

これは、マージ前の CI が落ちたときに、まず何をするかを決めるケースです。人手でやるなら、落ちたジョブのログを開き、テスト自体の不安定さなのかコードが壊れたのかを見て、もう一度回すか、直しに行くか、詳しい人を呼ぶかを決めているはずです。1日に何十回も出るので、最初の仕分けを機械に任せたくなります。

![CI 失敗の振り分け。入力の失敗ログから、cause の Choice、severity の Score、enough_info の Noul を経て、自動リトライ、自動修正、人に回す、ログを足して投げ直すの四つに分かれる](/images/jev-conf-case-ci.png)

- **入力**：失敗した CI ジョブのログと、変更のあったファイル。
- **聞くこと**：原因（Choice）、緊急度（Score）、材料の充足（Noul）。
- **出口**：自動でリトライ、自動修正を試す、人に回す、ログを足して投げ直す。
- **この節で見る読み方**：高い `confidence` が両端に出ます。値だけでは向きが分かりません。

質問は三つ、同じリクエストに入れます。

- Choice `cause`（原因）：`flaky_infra`（環境やテストの不安定さ）/ `real_regression`（コードの退行）/ `config_error`（設定の誤り）/ `cannot_tell`（判断できない）
- Score `severity`（急ぎ具合）：リトライで足りる / 数日中に直す / リリースを止める
- Noul `enough_info`（材料は足りているか）：「与えられた情報で、どの変更がこの失敗を起こしたか特定できる」

`enough_info` は Noul です。Noul は yes か no かを問う質問ですが、返ってくるのは true / false ではなく、**yes である確率**（0〜1）です。表の数字はこの確率で、ここでは「特定できる」が yes なので、**高いほど材料が足りている**という向きになります。Choice や Score と違って `confidence` は付きません。yes と no の二つしか答えがなく、この確率ひとつで分布が決まってしまうからです。

まずは、ログをどこまで渡すかを変えて測ってみます。

| state | cause | cause の confidence | enough_info |
|---|---|---|---|
| ログ全文（テスト名、アサーション差分、変更ファイル、ブランチ） | real_regression | 0.99 | 0.20 |
| テスト名のみ | cannot_tell | 0.78 | 0.06 |
| `CI failed.` のみ | cannot_tell | 0.99 | 0.04 |

一行目と三行目は、どちらも `confidence` 0.99 です。一方は原因を特定していて、もう一方は何も分かっていません。値だけで門を作ると、この二つが同じ扱いになります。見るべきは、その 0.99 が `real_regression` に付いたのか `cannot_tell` に付いたのかです。材料の減りを捉えているのは `enough_info` のほうで、0.20、0.06、0.04 と順に下がっています。

なお `enough_info` が聞いているのは「どの変更が原因か特定できるか」で、`cause` が聞いている原因の種類より細かい判断です。ログ全文で `cause` が 0.99 でも `enough_info` が 0.20 にとどまるのは、原因の種類は分かっても、どの変更かまでは特定できないからだと読めます。

ところで、ここで効いてくるのが、失敗履歴を `state` に足すことです。履歴はデータベースを引けば取れます。渡し方を二通り試しました。実行結果をそのまま配列で渡す形と、文章にまとめて渡す形です。

```
# 文章で
history: "This test passed on every run before commit 4f1a2c and has
          failed on every run since. That commit modified billing/invoice.py."

# 配列で
recent_runs: [{"commit": "9b3e1a", "result": "pass"}, ... ,
              {"commit": "4f1a2c", "result": "fail"}]
```

| state | cause | cause の confidence | enough_info |
|---|---|---|---|
| ログ全文のみ | real_regression | 0.99 | 0.20 |
| ログ全文 + 履歴を文章で | real_regression | 1.00 | 0.41 |
| ログ全文 + 履歴を配列で | real_regression | 1.00 | **0.68** |

どちらも `enough_info` は上がりました。履歴を足すこと自体は効いています。

意外だったのは、**文章にまとめたほうが低かった**ことです。筆者は「比較はコードで済ませ、結果を言葉にして渡すほうがよい」と予想していましたが、その向きには出ませんでした。ただし配列側には pass と fail の回数がそのまま入っていて、文章側の「それ以前はすべて成功」より情報が締まっています。表現形式の差なのか情報量の差なのかは、この2セルでは切り分けられません。言えるのは、**数値をそのまま渡すより言葉にしたほうがよいとは限らない**ということです。

さきほど予告した「低い `confidence` の一つ目の型」も、ここで観測できます。回帰ともフレーキーとも読める履歴（「同じコミット上で10回中2回だけ失敗、残り8回は成功」）を足したセルでは、`real_regression` 0.51 と `flaky_infra` 0.48 が拮抗し、`confidence` は 0.35 に落ちました。どちらの原因もありうる状態です。

:::message
**証拠が矛盾していれば割れる、ではありませんでした**

筆者ははじめ、`state` の中で証拠が食い違えば `confidence` が割れると考えて測りました。そうはなりませんでした。

上の二つの履歴、つまり「4f1a2c 以降のすべての実行で失敗」と「同じコミット上で10回中2回だけ失敗」を同時に入れると、この二つは両立しません。それでも `confidence` は 0.80 で、モデルは前者を採って後者を無視しました。一方、フレーキー側だけを入れた `state` は矛盾を含まないのに 0.35 でした。

割れを作るのは証拠の矛盾ではなく、**候補が拮抗していること**のようです。矛盾の検出をモデルに期待するなら、それ自体を Noul で聞くほうが確実です。
:::

振り分けはこうなります。

| enough_info | cause の confidence | 状態 | この回の処理 | 次に手を入れる先 |
|---|---|---|---|---|
| 足りている | 高い | 原因が特定できている | `cause` に応じて自動処理 | — |
| 足りている | 低い | 材料はあるが複数の原因が拮抗する | 人に回す | 候補を切り分ける材料の渡し方 |
| 足りていない | 高い | 材料がないまま答えている | 人に回す | 情報を集めて送りなおすか、`state` の作り方 |
| 足りていない | 低い | 何も言えていない | 人に回す | ログ収集そのもの |

自動で流せるのは一行目だけです。残る三つはどれも人に回りますが、**次に手を入れる先が違います**。ここを区別しないと、同じ「人に回った案件」の山から何を直せばよいかが分かりません。

そして `confidence` だけを見ていると、一行目と三行目が同じ顔をします。どちらも高い値が返るのに、片方は自動で流してよく、もう片方は絶対に流してはいけません。

:::message
**表の三行目について**

この行は、足りない情報を集めて投げ直すシグナルにも、`state` の作り方を見直すシグナルにもなります。どちらかは頻度で決まります。

たまにしか出ないなら、その回だけ情報が欠けていたと見て、集めて投げ直せば済みます。取得が高くつく情報を必要なときだけ引く設計なら、これが本来の姿です。一方、恒常的に出るなら、`state` を組み立てるコードのほうを疑います。CI の履歴や差分のように、データベースとリポジトリから毎回引けるものが抜けているなら、検知してから足すより最初から入れておくほうが素直です。
:::

### ケース2　社内イシューのトリアージ

これは、社内の問い合わせ窓口に上がってきた報告を、担当チームに渡すケースです。「経費精算の画面で申請ボタンが押せない」といった報告が、業務システムの数だけ別々の部署から届きます。読んで担当を決め、情報が足りなければ書き直しを頼む。この最初の仕分けが対象です。

![社内イシューのトリアージ。タイトルと本文から、team の Choice、urgency の Score、has_repro と enough_info の Noul を経て、自動割当、差し戻し、人が見るの三つに分かれる](/images/jev-conf-case-issue.png)

- **入力**：社内から上がってきたイシューのタイトルと本文。日本語のまま渡します。
- **聞くこと**：担当チーム（Choice）、緊急度（Score）、再現手順の有無と材料の充足（Noul 二つ）。
- **出口**：担当チームへ自動で割り当てる、書き直しを頼んで差し戻す、人が見る。
- **この節で見る読み方**：高い `confidence` は、入力の質を保証しません。

社外からの報告を対象にしないのは、`state` 経由の誘導という別の問題が絡み、本記事ではそれを測っていないためです。

日本語のまま投げて構いません。この四つの報告と質問文の言語を入れ替えて測った結果を、下にまとめました。

:::message
**質問や指示は英語にすべきか**

[公式ドキュメント](https://docs.typesafe.ai/models#language-support)は、英語が第一の訓練言語で精度が最も良く、CJK を含む他の言語も扱えるが同等ではない、と述べています。そのうえで、非英語で使う前に自分のデータで試すように、と付け加えています。二つ測りました。**正解できるか**と、**言語を変えても答えが動かないか**です。

**まず精度です。** 正解ラベルを先に決めた社内イシュー20件を、日本語版と英語版で投げました。うち8件は、表面の語がわざと違うチームを指すように書いてあります（「サーバーエラーが発生しました」と出るが、郵便番号にハイフンを入れたときだけなのでアプリの不具合、など）。

結果は日本語 20/20、英語 19/20 でした。この20例では、日本語での成績の低下は観測されませんでした。ただし20件は少なく、しかも筆者が作った例で、実運用の問い合わせから無作為に選んだものではありません。英語と同等だとも、実運用でどれだけ落ちるかとも言えません。

**次に一致度です。** `state`（報告の本文）と `questions`（`instructions` と `criteria`）は別々に言語を選べるので、組み合わせは四通りあります。実務で迷うのは二段目です。データは日本語でしか来ないが、指示だけ英語で書くべきか。

| `urgency`（Score の値） | state 日 / 質問 日 | state 日 / 質問 英 | state 英 / 質問 日 | state 英 / 質問 英 | 幅 |
|---|---|---|---|---|---|
| 手順あり | 1.20 | 1.36 | 1.34 | 1.46 | 0.26 |
| 手順なし | 1.40 | 1.22 | 1.55 | 1.36 | 0.33 |
| 「動きません」 | 1.51 | 1.45 | 0.99 | 0.97 | **0.54** |
| 手順が途中 | 1.29 | 1.12 | 1.54 | 1.27 | 0.42 |

**担当チーム（Choice）の答えは、どちらを訳しても16通りすべて一致しました。** ただし値は動いていて、`confidence` の幅は最大 0.12（他は 0.01 以下）、`has_repro` と `enough_info` は最大 0.08 でした。**緊急度（Score）の値は、それより大きく動きます**（最大 0.54）。 しかも `state` を訳しても `questions` を訳しても動き、向きが一定しません。

一つの解釈は、効いているのが言語そのものより判断の粒度だ、というものです。Score の目盛りは `criteria` の文が定義しているので、「今週中に対応する」と "Handle within this week" で含む切迫感が違えば、目盛りごとずれます。ただし Choice・Score・Noul はそれぞれ別のこと（担当・緊急度・再現手順）を聞いているので、型の違いと質問内容の違いは分離できていません。

もう一点。**唯一の誤答は `confidence` 0.37 で返ってきました。** この記事の振り分けは、モデルが常に正しいことより、間違うときに確信が低いことを当てにしています。この1件はそのとおりに振る舞いましたが、1件の観測なので、言語差があっても安全だと言えるほどの根拠にはなりません。

ただし気になる観測が一つあります。**最も言葉の足りない報告で、最も差が大きく出ました**（「動きません」だけの報告で 1.51 と 0.97）。日本語は主語や目的語を落とせるので、現場の言葉の足りない問い合わせでは英語版より情報が薄くなりがちです。テストに使った文は、それに比べればきちんと書けていました。

結論としては、日本語で始めて構いません。ただし Score の閾値は実際に使う言語で測り直し、誤答が低い `confidence` で来ているかを運用中に確かめてください。20件で、ベンダー自身が英語を最良としているのを覆したことにはなりません。
:::

質問は四つです。

- Choice `team`（担当チーム）：`infra`（基盤）/ `app`（アプリケーション）/ `account`（権限とアカウント）/ `cannot_tell`（判断できない）
- Score `urgency`（緊急度）：様子を見てよい / 今週中 / 即時
- Noul `has_repro`（再現手順があるか）：「報告者以外が同じ現象を再現するのに足りる手順が書かれている」
- Noul `enough_info`（材料は足りているか）：「この報告の内容だけで、どのチームが対応すべきか判断できる」

イシューの書かれ方を変えて測りました。

| イシュー | team | team の confidence | has_repro | enough_info |
|---|---|---|---|---|
| 手順、環境、期待と実際、影響範囲を記載 | app | 1.00 | 0.90 | 0.33 |
| 「申請ボタンが押せません。困っています」 | app | 0.90 | 0.06 | 0.24 |
| 「動きません」 | cannot_tell | 0.99 | 0.05 | 0.09 |
| 手順が途中で切れている | app | 0.98 | **0.25** | 0.22 |

ここで見ていただきたいのは二行目です。本文が一行しかないのに `team` は `app` を `confidence` 0.90 で返しています。担当の推測としては妥当で、実際 `app` で間違っていません。それでも、この報告をそのまま担当チームに流したら、担当者は何も調べられないでしょう。

`confidence` 0.90 が言っているのは「並べた四つの選択肢のうち `app` が抜けている」までです。報告が実装に着手できる質かどうかは、別の問いになります。

それを取っているのが `has_repro` です。完全な手順で 0.90、手順なしで 0.06、途中で切れた手順で 0.25。「手順:」という見出しの有無を拾っているだけなら四行目も高く出るはずなので、中身を見ていると考えられます。

一方 `enough_info` は、完全な報告でも 0.33 にとどまりました。ケース3では同じ名前の Noul が 0.65 を返しているので、比べると低く見えます。文言が違うからです。ここでの文は「この報告の内容だけで、どのチームが対応すべきか判断できる」で、報告がよく書けていても、症状だけでは基盤側かアプリ側か決めきれない場合があります。0.33 はそれを反映した値と読めます。

つまり **Noul の水準は質問文ごとに違います**。ケース3で使った 0.3 という境をここに持ち込むと、よく書けた報告が 0.33 とぎりぎりで通ることになります。境をわずかに上げれば落ちます。名前を `enough_info` で揃えても、聞いている内容が違えば別の尺度です。この案件で材料の充足を測っているのは `has_repro` のほうで、振り分けにもそちらを使います。

振り分けはこうなります。

- `team` が `cannot_tell`：報告者に何の話か聞く。
- `has_repro` が低い：再現手順を書いてもらう差し戻し。`team` の答えは使わない。
- `has_repro` が高く `team の confidence` も高い：担当チームに自動で割り当てる。
- `has_repro` が高く `team の confidence` が低い：担当が割れている。人が見る。

なお `has_repro` と `enough_info` は別々の Noul なので、足して 1 になることを期待しないでください。前述のとおり、Noul どうしは補完関係にありません。

### ケース3　ループを続けるか人を呼ぶか

これは、エージェントにテストを直させている最中に、そのまま走らせ続けてよいかを判断するケースです。放っておくと、同じ修正を何度も試して時間とトークンを溶かします。かといって一手ごとに確認を求めるなら、自走させる意味がありません。

:::message
**ここで扱うのは、止めるかどうかに判断の余地がある条件だけです**

予算の上限、実行時間の上限、本番環境への書き込み、認証情報への接触。この種の条件は、判定をモデルに委ねるものではありません。上限を超えたかどうかはコードが数えれば分かりますし、超えたなら確信度がいくつであろうと止める、というだけの話です。判断の余地がないものを確率で扱うと、本来ないはずの「通ってしまう経路」を自分で作ることになります。

この節が対象にするのは、そうした固い条件をすべて通過したうえで残る、「もう一手やらせるか、ここで人を呼ぶか」という柔らかい問いのほうです。
:::

![ループ制御。試行履歴から、next の Choice と enough_info の Noul を経て、続行、人に聞く、諦めて報告するの三つに分かれる](/images/jev-conf-case-loop.png)

- **入力**：自走中のエージェントが記録した試行履歴（何を変えて、結果がどうだったか）。
- **聞くこと**：次の一手（Choice）、材料の充足（Noul）。
- **出口**：そのまま続行、人に聞く、諦めて報告する。
- **この節で見る読み方**：材料が乏しいまま、高い `confidence` が出る場所です。

答えと材料の充足を別々に聞く必要が、ここで最もはっきり出ます。

- Choice `next`（次の一手）：`continue`（続行）/ `ask_human`（人に聞く）/ `stop`（中止して報告）
- Noul `enough_info`（材料は足りているか）：「記録された試行に、成功しそうな次の手を選ぶのに足りる情報がある」

`state` には試行履歴を入れて測りました。

`enough_info` は「足りる情報がある」が成り立つ確率です。ここでは 0.3 を境に読みます（この値は下のコードで使う閾値で、実測して決めたものではありません）。

| 試行履歴 | next | next の confidence | enough_info | 材料は |
|---|---|---|---|---|
| 3回試し、3回目で原因を特定（呼び出し側が引数を設定していない） | continue | 0.97 | 0.65 | 足りている |
| 1回試して「まだ失敗」だけ | **continue** | **0.93** | **0.14** | **足りていない** |
| 同じ修正を5回繰り返し、毎回同じ失敗 | continue | 0.17 | 0.13 | 足りていない |

二行目に注目してください。試行が一度きりで、結果も「まだ失敗」としか記録されていないのに、`continue` を `confidence` 0.93 で返します。一行目の 0.97 とほとんど変わりません。一方 `enough_info` は 0.14 で、一行目の 0.65 と明確に離れています。材料の不足を捉えているのはこちらです。

ただし `enough_info` が聞いているのは「成功しそうな次の手を選べるか」で、「続行してよいか」とは別の問いです。また、この状態で続行した結果が実際に悪かったかは測っていません。言えるのは、材料が乏しいと答えながら続行を強く推している、という組み合わせが出る、というところまでです。

三行目は性質が違います。`enough_info` は同じく低いのですが、`confidence` が 0.17 まで落ちています。`continue`、`ask_human`、`stop` に確率が散っている状態で、次の手が決まらないことを示しています。

以上から、門はこう置くことになります。

```python
if r.nouls["enough_info"].noul < 0.3:
    ask_human(reason="証拠が足りない")      # 二行目と三行目を両方捕まえる
elif r.choices["next"].confidence < 0.5:
    ask_human(reason="次の手が決まらない")
else:
    dispatch(r.choices["next"].choice)
```

肝心なのは順序ではなく、`confidence` が高くても `enough_info` の確認を省略しないことです。`confidence` だけで通すと、二行目（0.93）が素通りします。

### ケース4　レビュー指摘の採否

これは、自動レビューが出した指摘を、そのまま直すか人が見るかに振り分けるケースです。自動レビューを回すと、明らかに直してよいものから好みの問題まで、質の違う指摘が混ざって出てきます。全部人が見ると自動化の意味が薄れ、全部自動で直すと事故が起きます。

![レビュー指摘の採否。差分と指摘から、disposition の Choice と grounded の Noul を経て、自動修正、人の確認、棄却の三つに分かれる](/images/jev-conf-case-review.png)

- **入力**：差分と、自動レビューが出した指摘一件。
- **聞くこと**：処理の仕方（Choice）、指摘がコードに裏づけられているか（Noul）。
- **出口**：自動修正、人の確認、棄却。
- **この節で見る読み方**：`confidence` をそのまま閾値に使ってよい場合です。

ここまで注意点ばかりでしたが、`confidence` が素直に効く例も見ておきましょう。冒頭のコード例と同じ構成です。

- Choice `disposition`（処理の仕方）：`auto_fix`（自動修正）/ `human_review`（人の確認）/ `dismiss`（棄却）
- Noul `grounded`（コードに裏づけられているか）：「その指摘は、示された差分のコードによって裏づけられている」

性質の違う指摘を三つ投げました。

| 指摘 | disposition | disposition の confidence | grounded |
|---|---|---|---|
| 未使用の変数がある。削除せよ | auto_fix | 0.93 | 0.98 |
| 関数名を他と揃えるべきだ | human_review | 0.15 | 0.17 |
| `decimal.Decimal` の精度を設定していない（差分に該当箇所なし） | dismiss | 0.87 | **0.02** |

ここでは `confidence` が期待どおりに働いています。明白な指摘に 0.93、議論の余地がある指摘に 0.15。三つの選択肢はどれも実質的な処理を指していて、三件とも差分と指摘文を与えています。少なくともこの3件では、`confidence` の高低が指摘の性質と対応していました。

ただし、誤検知だけは `confidence` では捕まりません。三行目は `dismiss` に 0.87 と高い値が付いていますが、これは「棄却すべきだと確信している」であって、指摘が誤りかどうかの判定ではありません。それを取っているのが `grounded` で、0.02 を返しています。`grounded` が低いときは、`disposition` の値によらず自動では処理せず、差分の外のコードや規約を取りに行くか、人に回します。「示された差分に裏づけがない」は「指摘が誤り」とは限らず、根拠が差分の外にあるだけの場合もあります。自動で棄却するには、指摘が誤りだという根拠が別に要ります。

もう一点、二行目についても補足しておきます。`human_review` に 0.15 という低い値が付いたので「人が決めるべき案件だ」と読みたくなりますが、`cannot_tell` を足して測り直すと `cannot_tell` が確率 0.41 で最有力になり、`human_review` は 0.32 に下がりました。このプロジェクトの命名規約が `state` に書かれていないので、判断材料が無いというのが正確な読みです。つまりこれは「人が決めるべき案件」ではなく、「規約を `state` に入れれば決まる案件」でした。

### ケース5　ログ行の扱いを決める

これは、本番ログに流れてきた1行を見て、夜中に人を起こすかどうかを決めるケースです。条件をルールで書き下すと、サービスが増えるたびに書き足すことになり、誤報と見逃しの調整が終わりません。

![ログ監視。ログ一行から action の Choice を経て、無視、チケット起票、即時呼び出しの三つに分かれる](/images/jev-conf-case-monitor.png)

- **入力**：監視対象のログ一行。
- **聞くこと**：どうするか。Choice `action`（とるべき処置）：`ignore`（無視）/ `ticket`（起票）/ `page`（即時呼び出し）。
- **出口**：無視、チケット起票、即時呼び出し。
- **この節で見る読み方**：低い `confidence` の正体を、`cannot_tell` で見分けます。

ケース1で予告した「低い `confidence` のもう一つの型」を、ここで確認します。

| ログ行 | action | action の confidence |
|---|---|---|
| `retry 3/3 failed for charge ch_9f21: upstream returned 503`（1回目） | ticket | 0.27 |
| 同上（2回目） | ticket | 0.31 |
| 同上（3回目） | ticket | 0.29 |
| `retry 1/3 for charge ch_9f21: upstream 503` | ignore | 0.30 |
| `all retries failed for 4182 charges in the last 5 minutes` | page | 0.99 |

上の三行は、同じ行を三回投げて 0.27、0.31、0.29 と低いまま安定しています。ここで筆者は「一件の課金失敗を起票すべきかはモデルが決められる問題ではない。サービスの重要度も当直の人数も `state` に書かれていないのだから、閾値は人間が決めるしかない」と結論しかけました。

しかし、この3択には `cannot_tell` が入っていません。記事の前半で自分が書いたことを、自分で適用していなかったわけです。足して測り直しました。

| 選択肢 | 答え | confidence |
|---|---|---|
| 3つ（ignore / ticket / page） | ticket | 0.27 |
| 4つ（+ cannot_tell）1回目 | **cannot_tell**（確率 0.56） | 0.41 |
| 4つ（+ cannot_tell）2回目 | **cannot_tell**（確率 0.55） | 0.40 |

`cannot_tell` が最有力になりました。材料不足と読むのが自然です。ただし、ここで足した `cannot_tell` の説明文には「サービスの重要度や当直方針が書かれていない」と、足りない情報を具体的に書いていました。モデルがそれに引かれた可能性があり、汎用的な「判断できない」で同じ結果になるかは確かめていません。少なくとも、低い `confidence` を見て即座に「ここは人間が決める領域だ」と決めつけるのは早い、ということは言えます。

一方、ケース1で回帰ともフレーキーとも読める履歴を与えたセルは、`cannot_tell` を用意していても選ばず、候補が拮抗したまま割れました。`cannot_tell` の選ばれ方が低い `confidence` の中身を推す手がかりになる、というのが、この二つの観測から立てられる仮説です。

なお、この行を三回投げると 0.27、0.31、0.29 で、答えは三回とも `ticket` でした。ただし閾値を 0.30 に置いていれば、この程度の揺れでも判定は入れ替わります。最終行のように規模が桁違いになれば `confidence` 0.99 が返りましたが、1件の観測なので、その帯を自動で page に回すかどうかは、運用データで見逃しと誤報を評価してから決めてください。

## 受け取り方のまとめ

五つの事例で見た読み方を、観測から処理への対応として並べ直します。

### 観測から処理への対応表

![confidence と enough_info の二軸で作った 2x2 のマップ。右下の「材料なしで断言」の区画だけが着色され、自動処理に流してはいけない状態として示されている](/images/jev-conf-summary-map.png)

| 観測 | 読み方 | 処理 |
|---|---|---|
| 高い。実質的な選択肢に集中 | 並べた選択肢の中で一つが抜けている | 材料の充足を別途確認したうえで自動処理 |
| 高い。`cannot_tell` に集中 | 材料がない | `state` を足して投げ直す |
| 高い。`cannot_tell` を用意していない | 材料の有無が値から読めない | 選択肢の設計をやり直す |
| 低い。`cannot_tell` を出しても選ばれない | 候補が拮抗している（材料不足も併存しうる） | 人に回す |
| 低い。`cannot_tell` が最有力になる | 判断材料が足りない可能性が高い | `state` に足せる情報を検討する |

この表の三行目と、ケース3の二行目（`continue` 0.93 に対し `enough_info` 0.14）は同じ状態です。`confidence` だけを見ていると、材料のないまま出た高い確信が、材料の揃った高い確信と同じ顔をして現れます。

表の「人に回す」は、終点として書いていますが、実際には次の自動化の入口でもあります。ケース5では、閾値は人が決めるしかないと結論しかけた案件が、`cannot_tell` を足したら材料不足だと分かりました。サービスの重要度と当直方針を `state` に書けば、自動で流せる見込みがあります。人に回した案件が実際どう裁かれたかを記録しておくと、何が足りていなかったのか、どの条件なら自動で流せるのかが見えてきます。

`state` の作り方についても一点だけ。履歴を引くのも前回との差を取るのもコードのほうが正確で、引いた結果を `state` に足すと、CI のケースで `enough_info` が 0.20 から 0.41〜0.68 に上がりました。ただし文章にまとめるか数値のまま渡すかについては、ケース1で見たとおり、言葉にしたほうがよいという結果は出ていません。

```python
# 数値を並べて、差を取らせている
state = {"ビルド時間": 420, "直近平均": 180}

# 割り算はコード側で済ませ、出た結果を渡す
state = {"ビルド時間の傾向": "直近平均の 2.3 倍に増えている"}
```

### 閾値は行き先ごとに変える

ここまでは「閾値は文脈をまたいで持ち込めない」という話でした。選択肢の数が変われば目盛りが変わり、質問文が変われば水準が変わる。目盛りの側の問題です。

これとは別に、**同じ目盛りの上でも、行き先ごとに線を引く高さを変える**という話があります。[公式ドキュメント](https://docs.typesafe.ai/confidence#thresholds-scale-with-risk)はこちらを勧めていて、送金アプリの例を挙げています。残高を表示するだけなら間違えても画面を出し直せばよいので、0.5 を超えていればそのまま実行する。送金を承認するなら取り返しがつかないので、0.9 を超えていなければ利用者に確認を取る。同じ `confidence` の値を、行動の結果の重さで読み分けています。

この記事のケース4がちょうど同じ形です。`auto_fix`（自動修正）と `dismiss`（棄却）では、間違えたときの損害が違います。

```python
d = r.choices["disposition"]

if r.nouls["grounded"].noul < 0.3:
    human_review(finding)            # 裏づけが取れていない。値によらず人へ
elif d.choice == "dismiss" and d.confidence > 0.8:
    close(finding)                   # 棄却。誤ると正しい指摘を閉じてしまう
elif d.choice == "auto_fix" and d.confidence > 0.95:
    apply_fix(finding)               # 自動修正。誤ると誤った変更が入る
else:
    human_review(finding)
```

`dismiss`（棄却）と `auto_fix`（自動修正）では、誤ったときに起きることが違います。棄却を誤れば欠陥が残り、自動修正を誤れば誤った変更が入ります。どちらが重いかは、指摘の重大性や変更の範囲、あとから検証できるかで決まります。上の 0.8 と 0.95 は、その違いを示すための仮の値です。**どの行動をどの高さで通すかは、失敗したとき何が起きるかの問題なので、こちら側のコードが決めます。** モデルは「これは誤検知だと 0.87 の確信で思う」までしか言いません。

なお、この二つは別々に効きます。選択肢の数を変えれば閾値の値そのものは測り直しになりますが、行動ごとに高さを変えるという考え方のほうは変わりません。

### cannot_tell は常に入れるべきか

選択肢を1つ増やすことに副作用はないのでしょうか。材料が十分にあるケースで、選択肢だけを変えて測りました。

| 入力 | 選択肢 | 答え | その確率 | confidence |
|---|---|---|---|---|
| 明白なレビュー指摘（未使用変数） | 3つ | auto_fix | 0.95 | 0.92 |
| 同上 | 4つ（+ `cannot_tell`） | auto_fix | 0.86 | **0.82** |
| CI のログ全文 | 4つ（+ `cannot_tell`） | real_regression | 0.99 | 0.99 |
| 同上 | 3つ | real_regression | 1.00 | 1.00 |

この2件では、答えは変わりませんでした。`cannot_tell` が取った確率も 0.02 と 0.01 です。材料があるときに `cannot_tell` が答えを奪う、という様子はこの2件では見えませんでした。

ただし「無視される」とまでは言えません。レビューの例では `auto_fix` が 0.95 から 0.86 に落ちています。減った 0.09 の行き先は `cannot_tell`（+0.02）ではなく、多くが `human_review`（+0.06）でした。**選択肢を1つ足すと、その選択肢が確率を取るかどうかとは別に、分布全体がいくらか動きます。**

`confidence` が 0.92 から 0.82 に下がったのも、これが理由です。選択肢が増えたから下がったのではありません。式に `n` が入っているので、**peak が同じなら選択肢が多いほど confidence は上がります**（0.95 のままなら4択で 0.933）。実際に下がったのは、peak そのものが落ちたからです。

とはいえ閾値を選択肢数をまたいで持ち込めないことは変わりません。同じ peak 0.95 でも、3択なら 0.925、4択なら 0.933 と目盛りがずれます。

以上をまとめると、こうなります。

| | 内容 | 根拠 |
|---|---|---|
| 利点 | 材料不足が、根拠のない答えへの高い確信ではなく「判断できない」への確信として返る | `at_market` 0.93 が `cannot_tell` 1.00 に変わった |
| 利点 | 低い `confidence` の原因を見分けられる | 監視は `cannot_tell` 0.56、拮抗した CI の履歴は選ばず 0.51 対 0.48 |
| 副作用 | 材料があっても分布はいくらか動く。この2件では答えは変わらなかった | `auto_fix` 0.95 → 0.86。受け皿は `cannot_tell` ではなく `human_review` |
| 副作用 | `confidence` の目盛りが選択肢の数で変わる | 同じ peak 0.95 でも3択 0.925、4択 0.933 |
| 条件 | `cannot_tell` が返ったときに何を足すかを先に決めておく | 足せる当てがなければ、人に回すための遠回りにしかならない |
| 条件 | 閾値は選択肢の数ごとに測り直す | 3択の 0.9 と4択の 0.9 は同じ状態を指さない |

条件の二つが満たせるなら、入れて構いません。なお Score も事情は同じで、段階の刻み方を変えると水準が動きます（同じ判断が3段階で 0.44、6段階で 0.62 でした。ただし段階を増やすときは各段階の説明文も書き換えているので、刻み数だけの効果ではありません）。

### 閾値を較正したらバージョンを固定する

`jev-latest` は新しいリリースが出ると指す先が動きます。[ドキュメント](https://docs.typesafe.ai/models#aliases)も、特定のバージョンで `confidence` の閾値を調整したなら、エイリアスではなくバージョン ID（`jev-1.13.0`）を指定し、移行は自分のスケジュールで行うように書いています。ここまで見てきたとおり、`confidence` は選択肢の数を変えるだけでも水準が動く値なので、モデルが入れ替われば当然動きます。

レスポンスの `model` フィールドには、実際に答えたバージョン ID が入ります。判定を記録に残すなら、これも一緒に残しておきます。あとから閾値が合わなくなったときに、モデルが変わったのか `state` が変わったのかを切り分けられます。

### 測っていないこと

最後に、この記事が測っていない範囲をまとめておきます。

言語の比較は日本語と英語だけ、タスクもトリアージ一つです。精度の比較は20件しかないので、中程度の差は検出できていません。正解ラベルは筆者が付けたもので、別の割り当てを主張しうる事例も含みます。

履歴を配列で渡すか文章で渡すかの比較は、二つの `state` で情報量が揃っていません。表現形式そのものの効果は分離できていません。

入力がすべてダミーデータである点は、ケースの前に置いた注意書きのとおりです。また保存した実測結果は計 147 件（通信の再試行を除く）で、各セルは表現を一通りしか試していません。質問文を書き換えれば値は動きます。

Score の `confidence` は、段階数が増えるほど Choice 向けの開示式より高めの値を返しました。公式が Score について示しているのは「分布の要約である」までなので、それ以上は扱いません。

数値の桁が判断に影響する現象は、別のドメイン（架空の通貨）では大きく出ました。購買力を固定して桁だけ 1 万倍したところ、確率が 0.61 から 0.28 まで動きました。一方 CI ログで `30 s` と `30000 ms` を比べたときは、`confidence` の差は最大 0.09 でした（`3.8 GB` と `4080218931 bytes` の比較も行いましたが、後者は十進で 4.08 GB にあたり、量が一致していなかったので結果から除きます）。桁の効果がドメインによって大きく違うのか、それとも CI の例では他の手がかりが強すぎて表記の影響が埋もれたのかは、切り分けられていません。

`cannot_tell` の効果を見た実験のうち、監視とレビューの例では、`cannot_tell` の説明文に足りない情報を具体的に書いていました。汎用的な「判断できない」との比較はしていません。また、`cannot_tell` と材料確認の Noul を入れることで誤った自動処理がどれだけ減るかは、評価していません。

[ドキュメントが挙げている失敗モード](https://docs.typesafe.ai/model-jaggedness/jev-1.13)のうち、`state` が大きくなるほど精度が落ちる現象と、`state` に混入した誘導的な記述の影響は、本記事では測っていません。

## おわりに

`confidence` という名前は、人間が「自信」という言葉から連想するものと、実際に計算されている量とのあいだに距離があります。実際に計算されているのは分布の尖り具合であって、モデルが「どれだけ確かな根拠を持っているか」ではありません。この距離に気付かないまま閾値を置くと、材料が何もない判断が、最も自信のある判断として自動処理に流れていきます。

筆者自身、最初は逆の予測を立てていました。`state` から情報を削れば confidence が下がるはずだ、と。測ったら上がりました。理由は特定できていません。一つの解釈は、情報が増えるほど「そうとも言えるが、こうとも言える」という材料が増えて確率が割れ、情報が減れば割れる理由も消える、というものです。ただしこれは給与比較の Choice 系列での観測で、同じ系列の Score は単調ではなく、CI の材料削減では 0.99、0.78、0.99 と上下しました。

もっとも、ここで見たことの多くは、機械学習で以前から論じられてきた話と重なります。最も大きい確率を確信度とみなすことの限界、材料の乏しい入力での過信、答えが割れることと材料が足りないことの区別、「どれでもない」という出口を持たせる設計。今回はそれが型のついた API の上でも見えた、ということです。同じ形の返り値を持つ他のモデルでも同じ読み方が役に立つかもしれませんが、それは測っていません。

救いがあるとすれば、有望な対策が閾値のチューニングではなく、**選択肢の設計**という設計時の作業だったことです。「判断できない」という出口を用意すると、少数の例では材料不足がそこに集まりました。あとは材料の充足を別の Noul で聞き、`confidence` が高くてもその確認を省かない。この対策で誤った自動処理が実際にどれだけ減るかは、自分のデータで確かめる必要があります。

ループエンジニアリングで最初に決めるのは閾値だと思っていましたが、測ってみて手応えがあったのは、モデルに「答えない」という出口を与えるかどうかでした。型のついた答えは扱いやすい代わりに、返ってきた数値を無条件に信じたくなります。何を意味しているかは、ドキュメントを読み、手元のデータで測ってから決めるのがよさそうです。
