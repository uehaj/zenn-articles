## はじめに

NTTテクノクロスの上原です。

意味で行を探す grep（[sys1grep](https://github.com/uehaj/sys1grep)）を Claude Code で開発しています。
issue と PR が増えてくると、1つのセッションで「実装して、レビューして、マージして、次の issue を選ぶ」を回すのが苦しくなりました。
会話が長くなって文脈が圧縮されるたびに、どの PR がどこまで進んだかを取り違えるからです。

そこで、役割ごとにセッションを分けました。
分けてみると、どの層でも「LLM に判断させる部分」と「LLM に任せないほうがよい部分」の境目が見えてきました。
この記事では、その構成と境目の引き方を、数日回した実例とともに書きます。
cross-session messaging そのものの仕組みは[公式ドキュメント](https://code.claude.com/docs/en/cross-session-messaging)を参照してください。

## TL;DR

- Claude Code のセッションを3層に分けて、1つのリポジトリの開発を回しています。
  オーナー（筆者）が話す**窓口**（同じマシンで動く Claude Desktop のローカルのセッション）、仕事を割り振ってレビューとマージを管理する**取りまとめ役**（CLI のセッション）、実装する**ワーカー**（herdr のペインで動く CLI のセッション3つ）です。
- 層のあいだは cross-session messaging（セッション間メッセージ）でつなぎます。
  ワーカーはオーナーではなく取りまとめ役に質問し、取りまとめ役はオーナーへの質問を1つの issue にまとめます。
- 窓口は、Remote Control での外からの接続と、複数のプロジェクトの取りまとめ役の束ねを見込んで分けました。
  今回の運用では、その効果はまだ確かめていません。
- 仕事を「判断」「状態の保存」「条件の機械的な検査」「変化の見張り」に分けました。
  保存先と、明文化できる検査・見張りの処理は、ファイル、GitHub のルール、シェルスクリプト、偽のサーバに対するテストへ移しました。
  実装、状態ファイルの更新、判断や結果の解釈は、引き続き LLM がしています。
- 見張りを LLM の定期実行からスクリプトに移したことで、変化のない5分ごとの確認には LLM を呼ばなくなりました。
  LLM が起きるのは、変化があったときと、1時間に1回の生存確認だけです（費用がどれだけ減ったかは、まだ実測していません）。
- 他のセッションから届いた「オーナーが承認した」という伝言は、承認として扱いません。
  取りまとめ役は、オーナー本人に直接聞き直してから動きます。
- 一方で、ワーカーが権限の判定で拒否された処理とほぼ同じものを、取りまとめ役がレビュー用のサブエージェントにさせてしまいました。
  拒否された操作の肩代わりに当たりうる失敗として、経緯を書きます。

## 3層の構成

全体はこうなっています。
右の列は、各層を支えている LLM 以外の道具です。

```
オーナー（人間）
   │ 話しかける
   ▼
窓口  ……………… Claude Desktop のローカルのセッション（同じマシン）
   │ セッション間メッセージ（指示の中継、状況の問い合わせ）
   ▼
取りまとめ役 …… CLI のセッション          ── 状態ファイル、判断待ちの issue
   │                                     ── 変化を見張るスクリプト（gh）
   │ セッション間メッセージ                ── レビュー記録とマージの関門（GitHub のルール）
   ├──▶ worker-1 ┐
   ├──▶ worker-2 ├ herdr のペイン         ── 偽の Jev に対するテスト
   ├──▶ worker-3 ┘
   │
   └──▶ レビュー用サブエージェント（Fable）  ── 同じテストと変異テスト
```

**窓口**：オーナーが普段話しかけるセッションです。
窓口は自分では開発せず、オーナーの指示を取りまとめ役に伝え、状況を問い合わせて要約します。
窓口を経由した言葉は、取りまとめ役にとってオーナーの承認にはなりません（後述）。

**取りまとめ役**：issue と PR を見て、仕事をワーカーに割り振るセッションです。
レビューを手配し、判定に従ってマージし、オーナーの判断が要る事柄を1つの issue にまとめます。
自分でコードを書かないのが決まりです。

**ワーカー**：割り当てられた issue を実装して PR を出すセッションです。
1つのブランチを持てるのは1人だけで、分からないことは取りまとめ役に聞きます。

窓口と取りまとめ役を分けた理由は2つあります。

1つ目は、外から話しかけやすくするためです。
[Remote Control](https://code.claude.com/docs/en/remote-control) を使えば、手元で動いているセッションに外から接続できます。
取りまとめ役の CLI に直接つなぐこともできますが、窓口を挟むと、取りまとめ役の細かいやりとりを見ずに、指示と報告だけを受け渡せます。
外から触る必要がなければ、この理由での分離は要りません。
なお、今回の窓口は取りまとめ役と同じマシンで動く Claude Desktop のローカルのセッションで、メッセージはマシン内の経路で届いていました。
今回の数日間に、外から Remote Control で窓口に接続したかどうかは記録に残っていません。
Remote Control で接続する場合の条件は、[公式ドキュメント](https://code.claude.com/docs/en/remote-control)と、セッション間メッセージの[利用条件](https://code.claude.com/docs/en/cross-session-messaging#availability)を確認してください。

2つ目は、窓口を複数のプロジェクトの取りまとめ役の束ね役にできるためです。
取りまとめ役はプロジェクトごとに1つ置き、それぞれが自分のリポジトリの状態ファイルとワーカーを持ちます。
窓口はその上に1つだけ置き、オーナーの言葉を各取りまとめ役に振り分けます。

```
オーナー
   │
   ▼
窓口 ─┬─▶ 取りまとめ役（sys1grep）─▶ worker-1..3
      ├─▶ 取りまとめ役（別のプロジェクト）─▶ …
      └─▶ …
```

窓口には代償もあります。
伝言を1段増やすので、伝言の取り違えや、承認の聞き直しが増えます（後述）。

## 仕事を4つに分ける

右の列の道具を置いた理由は、仕事の性質の違いです。
取りまとめ役の仕事を、次の4つに分けて考えています。

**判断**：どの issue を誰に割り振るか、直し方をどう決め打つか、レビューの判定をどう読むか。
これは LLM に任せます。

**状態の保存**：誰が何を持っているか、何が決まったか、何を待っているか。
会話に置くと圧縮で欠けるので、ファイルと issue に置きます。
ただし、ファイルを書き直すのは取りまとめ役なので、中身が正しいかは LLM に依存します。
保存先を会話の外に出しても、正しさまでは保証されません。

**条件の機械的な検査**：テストが通るか、レビューの記録があるか、手元の版と PR の版が一致するか。
これはスクリプトや GitHub のルールに置きます。
判定の手順を固定できるので、LLM が毎回自分で確かめ方を組み立てるときのような、手順のぶれがなくなります。
ただし、ブラウザでのテストや GitHub への問い合わせの結果は、環境や時刻、外部の状態にも左右されます。

**変化の見張り**：issue や PR が動いたか。
これはシェルスクリプトに置きます。
動かしてもトークンを使わないからです。

以下の節は、この4つの分け方に沿った記録です。

## 状態を会話の外に置く

取りまとめ役のセッションも、いずれ `/clear` されるか、マシンの再起動で落ちます。
そのため、状態は会話ではなくファイルと issue に置きます。

**状態ファイル**：リポジトリの `workdir/coordinator-state.md`（コミットしない）に、方針、担当表、決め打ちしたこと、返事待ち、予算を書きます。
状況が変わるたびに取りまとめ役が書き直し、新しい会話は「このファイルと issue を読んでから始める」ことになっています。

今回、取りまとめ役の会話を `/clear` してから「状態ファイルと #211 を読んで取りまとめを続けて」と頼みました。
取りまとめ役は担当表から進行中の作業を拾い、ファイルの記述をそのまま信じずに、それぞれの worktree の状態（`git status`、`git log`）と PR の head を GitHub で確かめてから再開しました。
状態ファイルは再開の手がかりで、正しさの根拠は git と GitHub の側にあります。

**オーナー待ちの一覧**：オーナーの判断が要る事柄は、GitHub の1つの issue（[#211](https://github.com/uehaj/sys1grep/issues/211)）にまとめます。
項目ごとに選択肢と推奨案を書き、オーナーはチェックを入れるか番号で答えます。
会話の途中で質問を散発させずに済みます。

一方、元に戻せる設計判断は取りまとめ役が決め打ちで進めます。
決めた内容、理由、戻し方を状態ファイルと issue のコメントに残し、あとで報告します。

## ワーカーの起動

ワーカーは端末多重化ツールの [herdr](https://herdr.dev/docs/cli-reference/) のペインで起動しています。
取りまとめ役が自分でペインを分け、Claude を名前付きで立ち上げ、指示を送ります。

```bash
# herdr のペインの中で実行する（--current は自分のいるペインを指す）
herdr pane split --current --direction right --cwd "$PWD" --no-focus
herdr agent start worker-1 --kind claude --pane <pane_id> -- -n worker-1 --permission-mode auto
herdr agent prompt worker-1 "$(cat workdir/worker-1-prompt.txt)" --wait --timeout 120000
```

`-n worker-1` でセッションに一意の名前を付けています。
複数のセッションを確実に呼び分けるためです。

permission mode は、今回は取りまとめ役もワーカーも `auto` にそろえました。
受け手が届いたメッセージをすぐ処理するか、ユーザーの承認待ちにするかは、mode の分類と受信の設定で決まります（[公式ドキュメントの受信制御](https://code.claude.com/docs/en/cross-session-messaging#control-inbound-messages)）。
今回の受信設定では、双方を `auto` にそろえた状態で、メッセージが承認待ちにならずに届いていました。
同じ `auto` でも、受信を保留（hold）や拒否（refuse）にしていれば自動では届きません。

ワーカーに渡す指示は定型にしてあります。
要点はこうです。

- 起動したら取りまとめ役に「worker-1: 起動、作業待ち」と名乗り、割り当てを待つ。
- 割り当てられたら自分の worktree を作り、そのブランチの担当は自分だけ。他人のブランチには push しない。
- 判断に迷ったら、ユーザーではなく取りまとめ役に聞く。待つあいだは推奨案で進める。
- 権限の判定に拒否された操作は回避せず、取りまとめ役に報告する。
- 終わったら、ブランチ、head の SHA、PR、実行した確認、決め打ちしたことを報告し、作業待ちに戻る。
- マージはしない。

ワーカーの報告を、取りまとめ役はそのまま信じません。
「テストが通った」という報告は、リポジトリのオフラインテスト（実サービスの API キーや外部への通信を使わず、手元で動かす偽の Jev サーバに対して実行する）の件数で受け取ります。
レビューの側でも同じテストを自分の手元で回し直すので、報告の言葉ではなく、同じ道具の出力どうしを突き合わせることになります。
ただし、件数がそろっても、同じ版を同じ条件で確かめたことまでは保証されません。

## サブエージェントとワーカーの使い分け

この構成に落ち着く前は、実装も取りまとめ役のサブエージェント（Agent ツールで起動する子）に任せていました。
今回、それがうまくいかない場面に2回当たりました。

1回目は、実装中のサブエージェントが API への接続エラー（プロキシ経由の TLS 証明書エラー）で途中終了したときです。
サブエージェントには[再開の仕組み](https://code.claude.com/docs/en/sub-agents#resume-subagents)がありますが、このときは、作業していた worktree の記録が残っていないという理由で再開できませんでした。
書きかけの差分をパッチに退避し、新しいサブエージェントに同じ worktree で続きをさせました。
2回目は、そのサブエージェントが、コミットとスクリーンショットまで済ませたところで、親のプロセスごと終わっていたときです（push と PR はまだでした）。
どちらの回も作業が失われなかったのは、差分がパッチとして、コミットが worktree に残っていたからです。

この2回の観察から、数時間かかる実装は独立したセッションのワーカーに、数十分で終わって結果を返すだけの仕事（レビュー）はサブエージェントに、という分け方にしました。
ワーカーは取りまとめ役が `/clear` されても動き続け、herdr のペインに残っているので、人間が様子を覗くこともできます。

レビュー用のサブエージェントには、実装したモデルとは別のモデル（Fable）を使います。
レビューの依頼文には、前回のレビュー記録の場所、オーナーが決めた挙動、確かめてほしい観点を書きます。
レビューの結論は「マージ可」か「先に直す」のどちらかで、指摘には重大、中、低の重さを付けます。
レビューの中では変異テストもさせます。
本体のコードに意図的な誤りを入れ、既存のテストがそれを検出するかを確かめるもので、「テストを足した」という主張の中身を確かめられます。

## 1本の PR が通るまで

実際の例で流れを追います。
`--serve` で開くページの「?」の説明を、画面下の帯ではなく「?」の横に出す修正（[#214](https://github.com/uehaj/sys1grep/pull/214)）です。

最初のレビューに回した直後、同じファイルを触っていた別の PR（[#205](https://github.com/uehaj/sys1grep/pull/205)）が先にマージされました。
「同じファイルには担当を1人しか置かない」という決まりはありましたが、この2件は決まりを作る前から並行していました。
#205 の担当セッションがマージを知らせてきたので、取りまとめ役は `git merge-tree` で #214 との衝突を確かめました。
衝突していたので、古い版に対するレビューを止め、作成者に載せ直しを頼みました。
載せ直しでは、#205 で新しく増えた「?」13個にも同じ配置が効くように直させています。

載せ直した版のレビュー結果は「先に直す」でした。
スマホでタップして開く経路では、説明を画面内に寄せる処理が効かず、右側の説明が画面の外に切れていました。
作成者はマウスでしか確かめておらず、PR の本文にも「タップはブラウザで試していない」と書いていました。
レビュー用サブエージェントが、モバイル表示を真似たヘッドレスの Chromium でタップを試し、そこで見つけています。

修正は、空いていた worker-3 に割り当てました。
取りまとめ役は直し方を決め打ちで指示し（画面幅の測り方、上下にはみ出すときの向きの切り替え、閉じるときのフォーカスの扱い）、worker-3 が実装しました。
worker-3 の確認は、「?」17個、画面幅4通り、スクロール位置3通り、マウスとタップの2通りの組み合わせ408件で、横方向の余白と上端の条件を満たし、下に余裕がある場合は下端も画面内に収まったという報告でした。

再レビューの結論は「マージ可」でした（[レビュー記録](https://github.com/uehaj/sys1grep/pull/214#issuecomment-6110573895)）。
レビュー側は PR の版 `67b614f` について、組み合わせ673件（マウス340、タップ272、キーボード34、Details を閉じた状態27）を確かめ、設定した判定条件をすべて満たしました。
変異テストでは、12件の変異のうち11件でテストが失敗しました。
ただし、この11件はすべてが同じ質の検出ではありません。
1件はテストが例外で落ちたことによる検出で、もう1件は、テスト用の偽の window に `innerWidth` がなく、値が NaN になったことによる検出です。
後者は、実際のブラウザでの配置の崩れを再現して見つけたわけではありません。
検出できなかった1件は、幅0の要素を測らないための防御の行でした（実際のブラウザでは効いています）。
確かめたのはヘッドレスの Chromium だけで、実機、Safari、Firefox では確かめていません。

### マージの関門が守るもの、守らないもの

マージの直前には、取りまとめ役が小さなスクリプト（`scripts/reviewed.sh`）を実行します。
このスクリプトは、手元の HEAD が PR の head と一致することを確かめ、レビュー記録を PR にコメントし、head のコミットに `review` というステータスを付けます。
main ブランチの保護ルール（GitHub の ruleset「review before merge」）は、この `review` と CI 5本（`offline (node 20.16)`、`offline (node 22)`、`offline (node 24)`、`gitleaks`、`pack`）の成功を必須にしています（2026-10-12 に GitHub の API で設定を読んで確認）。
ステータスはコミットごとに付くので、レビューの後に誰かが push すると、新しい head には `review` がなく、そのままではマージできません。

この関門が保証するのは、通常の経路では、head のコミットに成功のステータスがそろっていなければマージが止まる、ということまでです。
守らないものもあります。
スクリプトが確かめるのは、記録のファイルが空でないことと、手元の HEAD が PR の head と一致することだけです。
記録の中身は読まないので、判定が「先に直す」のままでもステータスは付きます。
そのレビューが本当にその SHA を対象にしたか、未コミットの差分を含めていなかったかも検査しません。
GitHub の必須チェックも、レビューの内容を検証する仕組みではありません。
また、このルールは最新化の要求（strict）を有効にしていないので、PR の head が変わらないまま main だけが進んだ場合、最新の main を取り込んだ再検証まではこのルールで強制していません。
（設定は [GitHub の API](https://api.github.com/repos/uehaj/sys1grep/rulesets/23994244) で読んだものです。）
ルールはステータスを付ける主体を制限しておらず、管理者ロールはルールを迂回できます。
「重大と中の指摘がなければマージする」という判断は、引き続き取りまとめ役に依存しています。

### 推測ではなく問い合わせる

条件の検査を、推測から問い合わせに変えた例は、製品のコードの中にもありました。
オーナーが画面で見つけた不具合（[#222](https://github.com/uehaj/sys1grep/issues/222)）は、`--serve` をフォルダの指定で `-r` なしに起動すると、黙って起動し、検索のたびに「Is a directory」で失敗するというものでした。

修正の PR（[#223](https://github.com/uehaj/sys1grep/pull/223)）は、何度か作りが変わりました。
最初は起動時の引数だけを見ていて、環境変数や設定ファイルで渡した `-r` を見落としました（作成者が自分で気づいて取り下げ）。
次は、起動時に本体を試しに1回動かし、エラー文に「Is a directory」が出たら止める作りでした。
これはレビューで2回続けて「先に直す」になりました。
`--rank` を付けて起動すると、試しの実行が別のエラーで先に止まって判定をすり抜け、それを塞ぐと今度は `--template` や `--edges` で同じことが起きたからです。
エラー文の有無から状態を推測する限り、こうしたすり抜けは組み合わせの数だけ起こりえます。

取りまとめ役は、塞ぐのをやめて作り直すよう指示しました。
本体に判定専用の内部の入口を作り、オプションをすべて読み込んだ直後、組み合わせの検査より前に、`-r` が効いているかどうかを1行の JSON で答えさせます。
3回目のレビューで「マージ可」になり、確かめた組み合わせでのすり抜けはなくなりました。
ただし、判定の入口が答えを返せないとき（異常終了や時間切れ）は、警告を出して起動を続ける作りにしています。

## 見張りをスクリプトに渡す

取りまとめ役には、issue と PR の変化を見張る仕事もあります。
最初はこれを、セッションの中の定期実行（15分ごと）で、LLM 自身にやらせていました。

オーナーに頼まれて、その費用をセッションの記録（各リクエストの `usage`）から集計しました。
1回の確認は3回のモデル呼び出しで、キャッシュ読み込みは1呼び出しあたり平均約39万トークンでした。
2026-10-12 07:56〜10:06（日本時間）の定期確認10回（15分ごと。最初の1回の間隔だけ10分）の、1回あたりの平均と、`claude-opus-5-5` の API 定価（[価格表](https://platform.claude.com/docs/en/about-claude/pricing)）で換算した金額は次のとおりです。
トークン数は、1回の確認に含まれる3回の呼び出しの合計です（同じ文脈を3回読み直した分を含みます）。

| 種類 | トークン数 | 単価（100万あたり） | 金額 |
|---|---|---|---|
| キャッシュ読み込み | 1,182,800 | $0.20 | $0.2366 |
| キャッシュ書き込み（1時間保持） | 1,374 | $8.00 | $0.0110 |
| 出力 | 642 | $20.00 | $0.0128 |
| 通常の入力 | 8 | $4.00 | 約 $0 |
| **合計** | | | **約 $0.26** |

15分ごとに24時間回すと、1日96回で約 $25 になります。
これは API の定価による参考換算で、サブスクリプションの請求額や利用枠の消費量を示すものではありません。
この費用は、報告すべき変化があってもなくても、確認のたびにかかります。
1回あたりのキャッシュ読み込みは会話が伸びるにつれて増え、この10回でも約111万から約125万トークンへ増えていました。

そこで、見張りをシェルスクリプトに移しました。
スクリプトは5分ごとに gh で GitHub の状態を取り、要約（開いている issue と PR の番号、ラベル、更新日時、CI の結果、レビューの有無）を作って、前回の要約と比べます。
この比較では LLM を呼びません。
違いがあれば差分を出して終わり、その終了が取りまとめ役への通知になります。
60分変化がなければ、生存確認のために1回だけ終わります。
取りまとめ役は、起きたら差分を処理し、同じコマンドでスクリプトを起動し直します。

したがって LLM の費用は、変化があったときと1時間に1回の生存確認のときだけかかります。
生存確認の1回が今と同じ約 $0.26 だとすると、変化のない1日は約 $6 です。
ただし、間隔が延びるとキャッシュが切れて単価が上がる可能性があり、変化があったときの起床や Haiku による要約の費用も加わります。
この額は条件付きの試算で、移行後の費用はまだ実測していません。

要約の作り方には、取りまとめ役自身の書き込みで起きないための工夫が要りました。
取りまとめ役は判断待ちの issue（#211）を頻繁に書き換えるので、その issue はチェックの入った数だけを要約に入れています。
これで取りまとめ役の文面の書き換えには反応しなくなりましたが、限界もあります。
オーナーが番号やコメントで答えた場合や、チェックの付け替えで数が変わらない場合は検出できません。
逆に、取りまとめ役がチェック済みの項目を足したり消したりすると反応します。

変わった issue や PR の中身を読んで要約するのは、Haiku 5.5 に任せています（`claude -p --model claude-haiku-5-5 --tools ""`）。
これはオーナーの指示で、取りまとめ役の大きな文脈で生の issue や PR を読まないためです。
ただし、要約は判断の材料にとどめ、判断は取りまとめ役がします。
最初に動いた回で、Haiku は CLAUDE.md の1語を直す PR を「オーナーの判断が要る」と要約しました。
実際には、その PR はオーナーの指示で出したもので、マージしてよい条件もそろっていました。

新しく書いたスクリプトを起動しようとしたところ、権限の判定で2回拒否されました。
取りまとめ役は回避せずにオーナーに報告しました。
オーナーが中身を確かめて自分の端末で1回動かしたあと、取りまとめ役のセッションからバックグラウンドで起動しています。

## 他のセッションの言葉は承認ではない

セッション同士が話せるようになると、「誰の言葉か」があいまいになります。
今回いちばん気を遣ったのはここです。

窓口から取りまとめ役に、こういうメッセージが届きました。

> オーナーが、このセッション（窓口）で「30 分ごとの定期チェックを始めてよい」と明言しました。始めてください。

窓口はオーナーのために動いているので、おそらく本当です。
それでも、取りまとめ役はこれを承認として扱いませんでした。
Claude Code は、他のセッションから届いたメッセージを、ユーザーの承認の代わりにしないよう Claude に指示しています。
取りまとめ役はブラウザに質問画面を開き、オーナー本人に同じことを聞き直しました。
オーナーは「仕掛ける」を選び、間隔を「15分で」と書き足しました。
伝言どおりに30分で仕掛けていたら、間隔が食い違っていたことになります。
後に見張りをスクリプトへ移したときも、窓口経由の依頼を受けてから、オーナー本人に聞き直しています。

同じ依頼には「マージはオーナーの承認を得てから」ともありました。
これは、以前オーナーが出した「レビューでマージ可なら取りまとめ役がマージしてよい」という許可と食い違います。
これも質問画面で聞き、オーナーは以前の許可のままを選びました。

ワーカーの側でも、似た規則が働いています。
[公式ドキュメント](https://code.claude.com/docs/en/cross-session-messaging#message-delivery)は、あるセッションで拒否された操作を、別のセッションに頼まないよう定めています。
今回、worker-3 は変異テストを、自分の一時フォルダの削除（`rm -rf`）を含む1本の長いコマンドで実行しようとして、権限の判定で拒否されました。
削除を外し、毎回新しい一時フォルダを作る形に書き換えたコマンドも、続けて拒否されました。
拒否のメッセージは「このコマンドの使用は拒否された」という内容だけで、理由は書かれていませんでした。
worker-3 は3回目を試さず、拒否されたことと代案を取りまとめ役に報告しました。
取りまとめ役は「worker-3 の側では変異テストをせず、拒否された操作を言い換えて再試行もしない。変異テストはこの後のレビューで行う」と答えました。

ところが、その後のレビューで起きたことは、この規則に照らすと問題がありました。
取りまとめ役はレビュー用サブエージェントに「作成者は変異テストをしていない（結合したコマンドが拒否された）ので、あなたがやる」と依頼しました。
サブエージェントは自分の一時フォルダに PR の版を展開し、変異ごとにそのフォルダの中で `rm -rf` してから複製し、変異を入れ、サーバを起動してテストするスクリプトを書いて実行しました。
こちらは1度も拒否されていません。
変異の入れ方や複製元、フォルダの場所は違いますが、「削除を含み、複製して変異させ、サーバを起動する」という骨格は、worker-3 で拒否された処理とほぼ同じです。

取りまとめ役は当時、「拒否されたのはコマンドの形で、変異テストという作業そのものではない」と考えていました。
しかし拒否の理由は記録に残っておらず、この考えには裏付けがありません。
拒否された処理とほぼ同じものを、権限の判定が別になる別のエージェントにさせたことになり、公式ドキュメントが避けるよう定めている「拒否された操作の肩代わり」に当たりうると、今は考えています。
本来は、拒否されたことをオーナーに戻し、変異テストをどこでどう実行するかをオーナーに決めてもらうべきでした。

## うまくいかなかったこと

**返信できない相手がいた**：別のリポジトリのクラウドセッションから、Remote Control 経由の送信手段で疎通確認が届きました。
取りまとめ役の側には同じ送信手段がなく、名前でもセッション ID でも宛先が見つからず、返信できませんでした。
結局、返信文をオーナーに渡して、向こうに貼ってもらいました。
マシンやクラウドをまたぐと、届く経路と返す経路が対称にならないことがあります（条件は[公式ドキュメント](https://code.claude.com/docs/en/cross-session-messaging)に説明があります）。

**相手の状態を取り違えた**：そのクラウドセッションは、取りまとめ役が「idle で、レビュー修正をコミット済み、テスト再実行中」と報告していました。
実際には、それは取りまとめ役の状態ではなく、取りまとめ役に届いた別のワーカーの報告の中身でした。
一覧に出る状態と、メッセージの中身を、受け手が混同した例です。

**見張りもセッションに縛られる**：見張りのスクリプトは、取りまとめ役のセッションが裏で動かしています。
セッションが終われば止まるので、状態ファイルに「再起動したら同じコマンドで起動し直す」と書いて補っています。

## 3層でなければならないのか

この記事への最も強い反論は、「必要なのは3層の LLM ではなく、権限を分けた実行主体と、検証できる状態と手続きではないか」というものだと思います。
実際、この記事で効果があったものの多くは、層の数とは関係がありません。
変化のない定期起床を減らせたのは見張りをスクリプトに移したからで、再開できたのは状態を会話の外に置いたからで、うっかりマージを防いでいるのは GitHub のルールです。
状態の外部保存、機械的な検査、見張りの3つについては、1つのセッションでも同じ道具を置けば同じ効果が出るはずです。
並列の作業そのものは、1つのセッションでもサブエージェントでできます。
今回、実装を独立したセッションにしたのは、取りまとめ役の会話のクリアやプロセスの終了から実装を切り離すためです（同じマシンの障害や再起動までは切り離せません）。

この構成で確認できた利点は、もっと狭い部分です。
実装を取りまとめ役とは独立したセッションにしたことで、取りまとめ役の会話を `/clear` しても、ワーカーの実装は続きました。
窓口を分けたのは、外からの接続と複数プロジェクトの束ねを見込んだためです。
今回の記録では、その効果までは確認できていません（伝言の取り違えと聞き直しが増えるという代償のほうは、実際に起きています）。

反論が指摘するもう1つの点、判断が取りまとめ役に集中していることは、今の構成でも解消していません。
取りまとめ役は状態ファイルを書き、レビューの判定を読み、`review` のステータスを付けて、マージします。
レビューを別のモデルにさせているのは、そのうちの判定の部分を分けるためですが、ステータスを付ける権限はまだ取りまとめ役が持っています。

## おわりに

この構成で数日回した範囲では、筆者の実感として、細部に介入する回数が減りました（回数を数えて比べたわけではありません）。
オーナーは窓口に話しかけ、判断待ちの issue に答え、ときどき質問画面に答えることが主になりました。
ただし、2層や1セッションの構成と比べたわけではないので、3層化そのものの寄与は分かりません。

振り返ると、特に役立ったと感じているのは、セッションどうしのやりとりより、その下に置いた状態ファイル、検査、見張りのほうでした。
状態の保存は会話の外へ、条件の検査はスクリプトと GitHub のルールへ、変化の見張りはシェルスクリプトへ移し、LLM には割り振り、直し方の決め打ち、レビューの判定のように、今回ルール化していない判断を任せています。
道具に移しても正しさが保証されるわけではなく、ファイルの中身は書いた LLM に、関門の判定は付けた者に依存します。
それでも、どこが機械で確かめられていて、どこが LLM の判断に頼っているかが見えるようになりました。

セッション同士の言葉が増えるほど、どの言葉に権限があるかも決めておく必要が出てきます。
「承認はオーナー本人からだけ受け取る」「拒否された操作は肩代わりさせない」という2つの規則は、この構成の前提です。
ただ、前者は守れた一方で、後者については今回、拒否された操作の肩代わりに当たりうる処理を、取りまとめ役が別のエージェントに依頼し、実行させてしまいました。
指示の文面に規則を書くだけでは足りず、「拒否が起きたら、仕事を誰かに振り直す前にオーナーに戻す」ことを、取りまとめ役の決まりとして明文化する必要があると考えています。
もっとも、明文化した決まりを守るかどうかも LLM に依存します。
拒否の後の振り直しを機械的に止める仕組みや、レビュー結果を登録する権限を取りまとめ役から分ける仕組みは、今の構成にはありません。
